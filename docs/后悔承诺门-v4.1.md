# 后悔承诺门 v4.1：Agent 执行前审查层与可编辑工作记忆

> 版本：4.1 工程化修正版（删除原型关系章节）  
> 适用：自回归 Agent + 工具调用场景  
> 目标：在不可逆、难以反向修复的操作落地前，提供“草稿—自审—修改—提交”的审核窗口；只读无害操作自动放行，高危命令执行前自动拦截，等待模型再次自审后再提交执行。  
> 本版修正：  
> 1. 删除 v4.0 中“与已有原型的关系”章节；当前尚无完备原型验证，v4.1 为设计目标。  
> 2. 保留 v4.0 对“时间混乱”学术边界的修正；  
> 3. 保留“只读不等于免重算”的修正；  
> 4. 保留风险分级粒度、提交触发信号、依赖工具结果的高危调用处理；  
> 5. 保留“用户看到生成中的可见草稿”而非完整内部推理的表述；  
> 6. 保留多阶段状态机、安全信任模型、量化验收指标与实现路线图。

## 一、一句话概括

给自回归模型外挂一套 **“自动风险分级 + 草稿缓冲区 + 提交前审核 + 可编辑工作记忆”**。  
模型仍然只能往后写，但系统在检测到高危工具调用时自动拦截，把节点后的内容放入草稿缓冲区；模型可自审并用 `ctx_*` 修改本回合自己写出的内容。  
写草稿的过程用户可以看到模型正在写什么；写完后模型审核修改，然后替换界面上临时展示的草稿。  
错误 Token 及基于它算出的后续大片偏移结果，在下一回合的上下文中一起被蒸发；系统从编辑点直接开始重算，使编辑点之后的 KV cache 全部失效并重新计算，避免修改前残留影响继续参与注意力。

核心定位：**针对不可逆、难以反向修复的操作，在执行前提供修补机会。** 指令一旦落地确实无法撤销，但机制的价值在于落地前的审核窗口，而非事后回滚。

## 二、为什么需要它

### 2.1 自回归模型的结构缺陷

传统 Agent 的工作方式是：模型生成一段话或一个 tool call，立即执行，然后得到反馈。这带来四个问题：

1. **生成不可回退**  
   Transformer 只能往后写，不能倒带。token 一旦采样出来，就成为后续所有 token 的条件。

2. **生成即执行**  
   tool call 一写出来就落地：写文件、发邮件、下单、调 API。错误直接变成外部副作用。

3. **修正只能追加**  
   模型发现错了，只能在后续 token 里说“更正”。但错误 token 仍留在上下文里，继续参与注意力计算。

4. **错误会向下游扩散**  
   错误 Token 不只影响自身，还会在后续 Token 的隐藏状态中留下印记。后续 Token 会累积偏差，直到出现上下文漂移。  
   因此，只删除错误 Token 本身不够；基于它算出的下游偏移结果也应一并清除，并从编辑点重算下游。

### 2.2 关于“从编辑点重算”的学术边界修正

v3.1 引用了“简单编辑 KV cache 会导致时间混乱”的研究，但该表述存在过度推论。需要修正如下：

**已被研究支持的部分**  
- 在实时编辑场景（如代码编辑）中，把变动片段直接拼接进旧 KV cache，会导致位置冲突与 KV 更新错误。  
- 相关研究（如 ICLR 2025 的 PIE 工作）提出通过调整 RoPE 位置、在特定代码编辑实验中减少 KV 更新错误。  
- 这说明：**修改前缀后，下游缓存不能原样沿用**，是一个合理的工程问题。

**未被研究充分支持的部分**  
- 该研究并未证明所有错误上下文都会普遍产生“滚雪球式语义漂移”。  
- 该研究并未证明必须全量重算才能解决。  
- 该研究也指出，语义影响在其代码任务实验中相对较小。

**本机制的修正立场**  
- 从编辑点全量重算是**保证一致性的基准实现**，不是唯一可行方案。  
- 全量重算的实际成本必须测量，不能仅凭“约 10% 缓存破坏换约 100% 返工减少”的估算就认定代价可控。  
- 在本地推理中可控制 KV cache；在托管 API 中应表述为“使编辑点之后的前缀缓存失效并重新 prefill”，而非直接操作 KV。  
- 是否对某类任务采用全量重算、近似重算或局部复用，应由基准测试结果决定。

### 2.3 人类是怎么做的

人类处理重要操作时，不会“想一句发一句”。  
写邮件会先打草稿，读一遍，改错，再发送；写代码会先写一版，自己审阅，跑测试，再提交。  
AI 缺的正是这个“前额叶审核层”。

### 2.4 设计目标

- 只读、无害操作自动同意，不增加无谓审核成本。
- 高危、不可逆、命令执行类操作自动拦截，在落地前提供审核窗口。
- 允许模型修改本回合自己写的内容，并基于修改后的状态重新生成受影响的下游 Token。
- 写草稿的过程用户可见；写完后模型审核修改，再替换界面上临时展示的草稿。
- 不改变 Agent 主循环：调用—反馈仍然存在。
- 审核期间草稿有 IO 存档，最终落地 Token 流替换临时草稿。
- 对不可逆、外部化效果的操作，强制在提交前拦截。
- 用可测量的缓存破坏代价，换取后续轮次因基础错误返工导致的更大预输入消耗。
- 从编辑点重算，使编辑点之后的 KV cache 全部失效并重新计算，避免修改前残留影响。

## 三、核心机制

### 3.1 自动化风险分级

机制不再要求模型首调 `regret_gate`。系统根据工具类型与调用参数自动决定处理策略。

**分级粒度要求**  
仅按工具名称打标签不够。同一个工具（如 PowerShell）既能读取文件，也能删除数据。风险分级必须结合：
- 工具声明的基础 `effect_type`；
- 本次调用的参数与命令内容；
- 运行时策略与权限上下文；
- 目标资源敏感度（路径、URL、数据库、账户等）。

| 分级结果 | 系统行为 |
|---|---|
| 只读 / 无害 | 自动同意，立即执行，不进入审核窗口 |
| 可缓冲写 | 可进入草稿缓冲，提交点执行 |
| 命令执行 / 高危写 | 自动拦截节点，节点后内容进入待审草稿，等待模型再次自审 |
| 外部化 / 不可逆 | 强制拦截，必须审核后提交；必要时引入独立审核 Agent |

典型例子：  
- AI 读取文档、代码库、日志：纯读取，自动同意。  
- AI 执行 `pwsh` 命令、写文件、发请求、删除数据：系统在命令执行前自动拦截，节点后的内容等待后续再次自审。  
- 同一 `pwsh` 工具：`Get-Content` 可自动放行；`Remove-Item` 强制拦截。

### 3.2 核心对象

| 名称 | 含义 |
|---|---|
| 审核窗口 | 系统检测到高危工具调用时自动开启，允许模型提交 `ctx_*` 修改本回合草稿 |
| 草稿缓冲区 | 高危节点后的文本和工具调用先缓存，不执行、不展示为最终稿 |
| `ctx_insert / ctx_erase / ctx_replace` | 上下文手术提案：插入 / 抹除 / 替换本回合自己写的内容 |
| 射程锁 | 只能改本回合审核窗口开启后的 assistant/tool 草稿，历史与用户输入不可改 |
| 安全点 / 提交点 | 模型确认修改完成，系统一次性应用修改并触发工具执行 |
| 下游重算 | 错误 Token 及其下游偏移被蒸发后，从编辑点直接开始重算，后续 Token 在干净状态下重新生成 |
| 摘要 | 错误内容蒸发前留下精简经验，避免重复犯错 |
| 只读声明 | 工具可声明本次调用为只读、无需缓存保护；但只读不等于免重算，见 3.7 |
| `effect_type` | 工具副作用分层：`read_only` / `bufferable` / `externalized` / `irreversible` |
| 提交触发信号 | 明确定义什么动作代表“模型确认修改完成”，见 3.5 |

### 3.3 完整时序与状态机

本机制不是单次生成内可回退，而是一个多阶段状态机：

~~~text
GENERATE → INTERCEPT → REVIEW → APPLY → REGENERATE → COMMIT → EXECUTE → AUDIT
~~~

~~~text
[用户输入]
    │
    ▼
① 模型生成文本 + 工具调用
    │
    ▼
② 系统自动风险分级（工具类型 + 参数 + 策略）
    ├─ 只读 / 无害 ──► 自动同意，立即执行，返回结果
    └─ 高危 / 命令执行 / 不可逆 ──► 自动拦截节点，节点后内容进入草稿缓冲区
    │
    ▼
③ 审核窗口开启，模型可自审
   → 调用 draft { action: ctx_erase|ctx_replace|ctx_insert,
                  msg_ref: "tseq:N",
                  field: content|reasoning|tool_args|tool_result,
                  find/replace/text ... }
    │
    ├─ 审核窗口未开启 ──► 拒绝，提案作废
    ├─ msg_ref 指向历史/用户消息 ──► 射程锁拒绝
    └─ 校验通过 ──► 进入 pending（尚未生效）
    │
    ▼
④ 模型确认修改完成，提交（提交触发信号见 3.5）
    │
    ▼
⑤ 【安全点 / 提交点】系统一次性：
   a. 应用 pending 中所有手术
   b. 整对蒸发手术的 tool_call + role:tool
   c. 蒸发基于错误 Token 算出的下游偏移 Token 段
   d. 从编辑点开始重算 —— 使编辑点之后的 KV cache / 前缀缓存失效并重新计算
   e. 写入精简摘要
   f. 最终 Token 流交给 Agent 执行器
   g. 高危工具真正落地，返回反馈
    │
    ▼
⑥ 下一回合第一个请求发出时：
   payload.messages 里已无错误 Token、无下游偏移结果、无手术痕迹
~~~

关键变化：  
传统流程是“生成 → 执行 → 反馈”；  
本机制是“生成 → 自动分级 → 只读放行 / 高危拦截 → 草稿自审 → 从编辑点重算 → 提交执行 → 反馈”。

### 3.4 `ctx_*` 放行 / 拦截规则

| 条件 | 结果 |
|---|---|
| 审核窗口已开启，且 `msg_ref` 在本回合草稿范围内 | 放行，校验通过则入 pending |
| 审核窗口未开启 | 拦截：当前无待审高危操作 |
| `msg_ref` 指向历史轮 / 用户 / 系统消息 | 射程锁拒绝 |
| `find` 未命中 / 非法 field | 工具层校验失败，不入 pending |

射程锁：`tseq:N` 中的 N 必须 > 本回合高危拦截节点，且该消息 role ∈ {assistant, tool}。  
历史与用户输入永远不可改。

**结构化错误反馈**  
当 `ctx_*` 提案失败时，返回结构化错误信息：
- `failed_op_index`：第几个手术失败
- `failure_reason`：未命中 / 射程越界 / 非法字段 / 冲突
- `nearest_match_snippet`：最近似匹配片段
- `suggestion`：建议修正方向

错误信息控制在 200 Token 以内，超出部分用摘要替代。

### 3.5 修改期与提交触发

审核窗口开启后，若回合自然结束且 `pending` 为空，系统注入一次：

~~~text
[修改期] 当前存在待审高危操作。请审视本回合已写入的正文/思考/工具输出；若有错误，调用 draft 的 ctx_erase/ctx_replace/ctx_insert 提交修改；若无需修改，直接以纯文本结束本回合。
~~~

一个审核窗口只给一次修改期提示。若 `pending` 已有提案，跳过提示，直接进入安全点。

**提交触发信号必须明确**  
v3.1 只写了“模型确认后提交”，但未定义具体动作。建议明确为以下之一或组合：
- 模型调用专用 `commit` 工具；
- 模型以特定标记结束当前响应（如 `<<COMMIT>>`）；
- 模型在修改期内不再提交新 `ctx_*`，并以纯文本结束本回合；
- 系统在修改期提示后等待一个固定窗口，超时则按“无修改”处理。

不同实现可选择不同信号，但必须在协议中写明，避免歧义。

**依赖工具结果的高危调用**  
如果高危调用需要依赖尚未执行的工具结果，不能先拦截再审、又要求模型在提交前看到结果。处理策略：
- **逐步审核提交**：允许模型生成一个不依赖结果的高危调用批次，先审核提交执行，拿到结果后再生成下一批。
- **预执行只读依赖**：若依赖调用为只读，可先放行只读部分，拿到结果后再审核高危部分。
- **显式声明依赖**：工具调用可声明 `depends_on`，系统按依赖顺序分批审核与提交。
- **禁止**：不得让模型在未获得结果时假装已知结果并据此提交高危操作。

**自审能力分层**  
- 语法、命名、格式错误：自审有效，修复成功率较高。
- 逻辑、断言、边界条件错误：自审容易被错误前提带偏，成功率较低。
- 第三方无缓存 LLM 完整读取当轮操作来审核逻辑问题，成本过高；当前无法解决这一成本约束，只能优先使用自审节约成本。
- 不可逆高危操作可引入独立审核 Agent，只传入操作本身和预定义检查清单，不传入完整上下文。

### 3.6 安全点应用与蒸发

1. **原子性**：在副本上试应用；任一条失败则整批不生效、不蒸发。
2. **成功后**：
   - 按 `field` 写入修改后的内容；
   - 蒸发手术对应的 `role:tool`，并从 `assistant.tool_calls` 剥掉手术 id；
   - 若 assistant 无剩余 call 且无正文，整条丢弃；有正文则只剥 tool_calls、保留正文。
3. **下游偏移蒸发与从编辑点重算**：
   - 错误 Token 修正后，模型在修改后的新 Token 上继续推论，重新生成受影响的下游 Token。
   - 基于错误 Token 做出的错误下游决定，其对应 Token 段一并蒸发。
   - 蒸发范围包括：错误 Token 本身、基于它算出的下游偏移 Token 段。
   - 从编辑点开始重算，使编辑点之后的 KV cache / 前缀缓存失效并重新计算。
   - 重算范围限定在本回合内、尚未提交执行的 Token 段；已提交执行的部分只能走补偿/回滚。
4. **摘要**：摘要只需写“这里错了，不应走这条路”，并标注受影响的后续 Token 范围。若下游已有大量 Token 依赖错误内容，额外标注“下游依赖段需重新检查”。
5. **审计**：写 `ctx_applied` 事件，记录 turn、条数、op 列表、蒸发范围、重算范围。
6. **提交执行**：安全点应用完成后，最终 Token 流交给 Agent 执行器，工具真正落地。
7. **轮次耗尽**仍存在 pending → 仍会应用，不静默丢弃。

### 3.7 缓存策略、只读声明与重算边界

**核心判断**：修改本回合 AI 写出的内容，对 KV cache 的破坏范围有限，收益可能大于代价，但必须实测。

- AI 读取文档、代码库等只读操作通常是预输入大头，可声明为只读、无需缓存保护。
- 真正需要审核的高危操作在上下文中占比不高，且位于尾部。AI 输出在单轮逻辑轮中占比约 10%，修改这部分最多破坏当轮逻辑轮上下文的 10% 左右。
- 若因未审核导致返工，模型倾向于整篇重读而非复用缓存，预输入消耗可能增加约一倍。
- 用约 10% 的缓存破坏换取返工减少约 100%，是**待验证的工程假设**，不是既成结论。
- 从编辑点重算会破坏编辑点之后的 KV cache，但也正是这一破坏确保了时间一致性。

**只读不等于免重算**  
v3.1 将 `read_only` 视为免重算的充分条件，这是不准确的。工具是否改变外部状态，与它的结果是否影响模型后续生成，是两回事。

- 只读操作不改变外部状态，但其结果可能被后续内容引用。
- 如果手术修改了已被后续内容引用的只读结果，同样需要重算或明确接受近似。
- 因此，是否重算应依据**该内容是否被下游引用、引用深度、语义影响范围**来判断，而非仅看 `read_only` 标签。
- 只读声明可用于放宽缓存保护策略，但不能单独作为免除重算的依据。

**托管 API 与本地推理的差异**  
- 本地推理：可直接控制 KV cache，按编辑点截断并重算。
- 托管 API：无法直接操作 KV cache，应表述为“使编辑点之后的前缀缓存失效并重新 prefill”，具体是否复用由 provider 决定。
- 实现文档应分别给出两套路径，不能混为一谈。

### 3.8 副作用分层与事务缓冲

| `effect_type` | 含义 | 审核策略 |
|---|---|---|
| `read_only` | 读文档、查日志、只读查询 | 自动同意，立即执行；若结果被下游引用，手术修改时仍需评估重算 |
| `bufferable` | 写本地文件、构建操作、生成代码 | 草稿缓冲，审核通过后一次性应用 |
| `externalized` | 发 API 请求、写远程数据库、调用外部服务 | 草稿缓冲 + 执行前确认；发出后无法本地撤回，但机制确保发出前已审核 |
| `irreversible` | 删数据、发邮件、执行支付、危险 pwsh 命令 | 强制拦截，从该节点开始拦截后续所有操作，写完草稿后让 AI 审查一遍，再提交执行 |

**关键澄清**：本机制不是事后回滚工具。外部化效果一旦发出确实无法撤回，但整套机制的目标正是在不可逆操作**执行前**提供修补机会。`effect_type` 用于决定拦截强度和审核方式，而非改变“执行前审核”的核心定位。

### 3.9 高危操作强制拦截与独立审核

- 当模型传入 `irreversible` 或高危命令执行类工具时，系统强制从该节点开始拦截后续所有操作，直到模型完成自审并提交。
- 审核范围从单次调用扩展到整个高危操作链。
- 对于逻辑复杂的高危操作，可引入独立审核 Agent：只传入操作本身和预定义检查清单，不传入完整上下文。审核 Agent 输入可控制在几千 Token 以内，成本约为单次生成成本的 1.1–1.2 倍。
- 预定义检查清单示例（代码/命令场景）：
  - 语法可解析
  - 导入完整
  - 边界条件已处理
  - 异常路径已覆盖
  - 权限与路径合法
  - 幂等性确认（如适用）
  - 命令作用域与目标确认

### 3.10 外部验证器方向信号

自审修逻辑错误效率低，可引入外部验证器提供**方向性信号**：
- 类型检查器：类型签名不匹配
- dry-run 执行器：API 返回 404 / 文件路径不存在
- 静态分析工具：潜在空指针 / 资源泄漏
- 测试运行器：断言失败位置

外部验证器总结操作结果方向，并将方向信号回输入模型修改开始前，为自审提供方向。信号附带置信度标注，模型可忽略低置信度信号。

### 3.11 用户可见性与审计

**实时草稿可见**  
- 模型写草稿的过程，用户可以实时看到模型正在写什么。  
- 用户看到的是模型正在生成的**可见草稿**，而非最终稿，也不等同于模型内部未输出的推理过程。  
- 这一设计既保持了过程透明，也让用户可以在必要时人工介入判断。

**审核与替换**  
- 写完草稿后，模型进入审核窗口，自审并可能提交 `ctx_*` 修改。  
- 审核期间，界面上仍展示“审核中”的临时草稿，附带 IO 存档可供复查。  
- 审核完成后，最终落地的 Token 流直接替换界面上临时展示的草稿 Token 流。  
- 替换动作有视觉提示（如“内容已更新”），避免用户混淆草稿与最终稿。

**审计侧**  
- 草稿信息流有 IO 存档留档，可供复查。  
- 审计侧保留不可变记录：草稿、修改、蒸发范围、重算范围、提交、执行结果，全部可追溯。  
- 用户可见性与审计留档相互独立：用户看到的是“当前状态”，审计看到的是“完整时间线”。

## 四、关键设计决策与取舍

### 4.1 只改当前回合，拒绝改已落地 Token

保护 KV cache / 前缀缓存。修改历史会破坏缓存，导致大片重算。限制在当前回合，影响范围有限。只读操作可声明无需保护，进一步缩小缓存保护范围。

### 4.2 commit 之后不可后悔

人类审完执行完代码，也无法回滚。世界不可后悔是本质，commit 边界划在哪里是设计选择。把不可后悔窗口压到“执行前”，已经是能做到的最好。

### 4.3 前置消除显著降低漂移

错误 Token 的隐藏影响会累积。每轮在苗头出现时直接掐掉影响，后续漂移会显著降低。越早 Token 的轻微偏移，对后续影响越严重；前置消除正是针对这一点。

### 4.4 自动化风险分级，而非模型自主开关

模型自主判断开关可能不可靠：可能在高风险任务上觉得“简单”而不开，或在低风险任务上过度开。  
改为系统自动分级：只读自动同意，高危自动拦截，不可逆操作强制审核。分级需结合工具声明、调用参数与运行时策略。

### 4.5 用户可见性分级

写草稿的过程用户实时可见，模型写完草稿后审核修改，再替换界面上临时展示的草稿。  
这样用户既能看到模型的可见草稿过程，又能看到审核后的最终结果，避免“用户看到旧版、模型记得新版”的错位。注意：可见草稿 ≠ 完整内部推理过程。

### 4.6 删除错误 Token 留摘要

错误 Token 不只是噪音，也记录“为什么错”。直接蒸发会丢失教训。做法：蒸发错误 Token 及下游偏移，但留一条精简摘要。

### 4.7 副作用分层

`effect_type` 决定审核强度：只读自动放行，`bufferable` 走草稿缓冲，`externalized` 执行前确认，`irreversible` 强制拦截 + 独立审核。核心始终是执行前审核，而非事后回滚。

### 4.8 下游偏移蒸发与从编辑点重算

错误 Token 会污染下游 Token。清除必须扩展到下游：蒸发基于错误 Token 算出的偏移 Token 段，并从编辑点开始重算。  
从编辑点重算的关键意义：使编辑点之后的 KV cache / 前缀缓存失效并重新计算，使后续 Token 的 KV 对基于编辑后的上下文重新算出。  
但需注意：全量重算是保证一致性的基准实现，不是唯一方案，其成本必须实测。是否对某类任务采用全量重算、近似重算或局部复用，应由基准测试结果决定。

## 五、定位与适用场景

### 5.1 它不是通用后悔药

- 不能提升模型基础智能；
- 不能保证逻辑正确；
- 不能替代外部验证；
- commit 后失败仍需补偿或回滚。

### 5.2 它是执行前审查层

适合：
- 代码生成；
- 高危工具调用（写文件、发邮件、下单、调 API、执行 pwsh 命令）；
- 长程任务；
- 错误后果大、状态漂移小的场景。

价值：
- 降低不可逆错误率；
- 减少错误 Token 及其下游偏移对后续注意力的污染；
- 支持计划回滚和局部重写；
- 为工具调用引入事务语义；
- 产生高质量训练数据；
- 支持多候选、验证器、dry-run、投票；
- 有潜力成为 Agent Runtime 的标准层。

---

## 六、潜力

1. **降低不可逆错误率**：高危操作走草稿缓冲区，模型自审后才 commit。
2. **减少错误污染**：错误 Token 及下游偏移在下一回合 wire payload 里消失。
3. **支持计划回滚和局部重写**：提交前重构计划、替换参数、删除错误推理，并从编辑点重算下游。
4. **工具事务语义**：只读立即执行、写操作暂存、依赖分批、幂等键、条件提交、补偿事务。
5. **高质量训练数据**：“草稿—修改—提交”形成偏好对，可用于 DPO、RL、critic 训练。
6. **多候选和验证器组合**：草稿缓冲区可扩展成多版本、多分支、投票、外部 critic、dry-run、类型检查、权限检查。
7. **Agent Runtime 标准层**：可编辑工作记忆 + 执行前审核 + 工具事务提交 + 不可变审计。

---

## 七、边界与不足

### 7.1 自审悖论

自己审自己，盲区相同。模型能抓格式、参数、明显矛盾，但很难抓知识错误和逻辑偏差。  
解法：形式化错误靠自审 + 外部验证器方向信号；逻辑错误靠独立审核 Agent + 预定义检查清单；知识盲区靠外部知识源验证。

### 7.2 代码逻辑错误自审最难抓

语法错、参数错、边界条件漏、并发假设错、算法复杂度爆炸、业务逻辑理解错、异常路径没处理。  
语法检查、类型检查、dry-run 能抓一部分，但逻辑错误只能靠测试、形式化验证或人类判断。  
定位：减少低级错误和冲动操作，不保证逻辑正确。

### 7.3 “干净”的定义内隐

模型认为改干净了，不等于真的干净。可能过度修改、修了表面没修根因。  
解法：后训练 + 外部验证 + 规则校验。

### 7.4 模型自主判断开关不可靠

已改为系统自动风险分级：只读自动同意，高危自动拦截，不可逆强制审核。分级需结合参数与策略，不能只看工具名。

### 7.5 摘要可能成为新的错误 Token

摘要由模型自己写，可能归因写错、总结成错误规则、太简略。  
改进：摘要轻量化，只写“这里错了，不应走这条路”，并标注下游依赖段。定期合并相似摘要，长期未引用摘要降权。

### 7.6 训练与推理不匹配

机制是 runtime 外挂的。模型训练时没有“草稿—审核—提交”概念，推理时可能把审核当形式、过度自审、不知道何时停。  
解法：厂商在训练阶段引入类似流程，或用偏好学习教模型“什么样的修改值得做”。

### 7.7 commit 后失败仍需补偿

提交后工具执行失败、部分成功、外部状态变化，只能补偿或回滚，不能蒸发。  
需要 saga、幂等键、条件提交。本机制核心价值在提交前审核，而非提交后回滚。

### 7.8 审计必须保留原始草稿

用户看到的是“当前状态”的草稿和最终稿，但审计侧必须保留不可变记录：草稿、修改、蒸发范围、重算范围、提交、执行结果。

### 7.9 多回合摘要累积漂移

每轮前置消除降低漂移，但摘要链本身可能累积信息损失。  
缓解：每 N 轮做一次锚定检查，重新注入原始任务目标，确认当前路径仍服务于原始目标。

### 7.10 下游重算的边界

若错误 Token 的下游影响已扩散到本回合之外，无法在本回合内完全清除。重算范围建议限定在本回合内、尚未提交执行的 Token 段。已提交执行的部分只能走补偿/回滚路径。

### 7.11 重算完整性与成本

从编辑点重算虽能规避时间混乱，但重算必须完整覆盖所有受影响的 KV 段；若重算不完整（例如部分 KV 被复用而部分重算），仍可能残留时间不一致。  
实现上需要严格界定“编辑点”和“重算边界”，确保编辑点之后的 KV cache 全部失效并重新计算，不做局部复用。  
同时，全量重算的成本必须测量，不能仅凭估算认定代价可控。

### 7.12 安全信任模型

工具声明 `read_only: true` 不能作为唯一依据。权限系统必须由 runtime 注册表、沙箱和策略决定。否则恶意工具或 prompt injection 可以伪造只读声明，绕过审核。  
建议：工具风险元数据由系统注册与签名，调用参数经策略引擎评估，敏感操作强制人工或独立审核。

### 7.13 提交触发与依赖结果的处理

提交触发信号必须明确，依赖工具结果的高危调用必须分批处理。否则模型可能在未获得结果时假装已知结果并提交高危操作。

## 九、常见误用

| 错误 | 后果 |
|---|---|
| 审核窗口未开启就调 `ctx_*` | 拒绝，提案作废 |
| `msg_ref` 指向上一轮或用户输入 | 射程锁拒绝 |
| 指望“边说边改、立刻生效” | 修改在提交点才落地 |
| 以为改了就省了当前这一轮的注意力 | 当前回合已发出的请求无法追回；下一回合起才真正省注意力 |
| 以为 commit 后还能后悔 | commit 后世界已变，只能补偿 |
| 以为自审能发现所有错误 | 自审只能抓能力范围内的疏忽，不能抓知识盲区 |
| 对所有工具一视同仁 | 应区分 `effect_type`，并结合调用参数分级 |
| 只按工具名分级 | PowerShell 读写不分，会漏拦高危命令 |
| 忽略只读声明 | 只读段可免缓存保护，不声明会浪费缓存预算 |
| 把只读当免重算充分条件 | 只读结果被下游引用时，修改仍可能需重算 |
| 只删错误 Token 不删下游偏移 | 错误影响仍残留在下游 Token 中，漂移继续累积 |
| 只删 KV 条目不重算下游 | 后续 Token 的 KV 对可能仍反映编辑前状态 |
| 以为下游重算可以跨回合 | 已提交执行的部分无法在本回合内清除，只能走补偿/回滚 |
| 把可见草稿当完整思考过程 | 界面展示的是生成中的可见草稿，不是模型内部未输出推理 |
| 把设计目标当已有能力 | v4.1 是设计目标，尚无完备原型验证 |
| 提交触发信号不明确 | 模型与系统对“何时提交”理解不一致，导致误提交或漏提交 |
| 依赖结果的高危调用未分批 | 模型在未获得结果时假装已知结果并提交，造成错误执行 |

## 十、实现路线图

### 阶段 0：基线测量
- 在无审核机制下，测量长任务的成功率、错误率、返工率、预输入长度、延迟。
- 建立对照组，为后续验证提供基准。

### 阶段 1：MVP——高危拦截与草稿重写
- 实现工具风险注册表（系统声明，不信任模型）。
- 实现高危工具拦截与草稿缓冲。
- 实现 `ctx_*` 手术与提交点应用。
- 暂不实现 KV 重算，仅验证草稿—审核—提交流程。

### 阶段 2：提交与重算流程
- 明确提交触发信号。
- 实现依赖工具结果的分批审核。
- 实现从编辑点重算（本地推理路径）。
- 记录蒸发范围、重算范围、审计事件。

### 阶段 3：托管 API 适配
- 实现前缀缓存失效与重新 prefill 路径。
- 测量托管 API 下的额外 token 成本与延迟。
- 对比本地与托管路径的差异。

### 阶段 4：审核升级
- 引入外部验证器方向信号。
- 引入独立审核 Agent + 检查清单。
- 按风险等级升级审核强度。

### 阶段 5：量化评估与优化
- 对比阶段 0 基线，测量成功率、后续输入长度、延迟、缓存命中率。
- 根据结果决定是否采用全量重算、近似重算或局部复用。
- KV cache 优化等基线结果出来后再决定。

## 十一、给接收方的最短结论

1. **自动化分级**：只读自动同意；高危命令、写操作、不可逆操作自动拦截；分级需结合调用参数。  
2. **草稿缓冲**：高危节点后的文本和工具调用先缓存，不执行、不展示为最终稿。  
3. **实时可见**：模型写草稿过程用户可见；写完后模型审核修改，再替换界面上临时展示的草稿。  
4. **修正**：审核窗口内用 `draft.ctx_*` 提案，只能改本回合自己写的 assistant/tool 字段。  
5. **提交**：提交触发信号必须明确；安全点一次性应用修改 + 错误 Token 及下游偏移蒸发 + 从编辑点重算 + 写摘要。  
6. **执行**：最终 Token 流交给 Agent 执行器，高危工具真正落地，返回反馈。  
7. **效果**：下一回合起，发给模型的上下文里已无错误 Token 及其下游偏移结果。  
8. **重算边界**：从编辑点重算是保证一致性的基准实现，成本需实测；只读不等于免重算。  
9. **定位**：这是代码生成/高危工具调用场景的执行前审查层与可编辑工作记忆，不是通用后悔药。  
10. **依赖**：自审能力靠模型厂商后训练；外部验证、事务补偿、不可变审计仍需配套。  
11. **副作用分层**：用 `effect_type` 区分工具风险，不可逆操作强制拦截。  
12. **缓存取舍**：只读操作声明免保护，修改集中在尾部高危段，代价待实测。  
13. **集成路径**：后续可作为核心、深度嵌入机制，适配 Provider 原生 context editing。  
14. **实现状态**：目前尚无完备原型验证，v4.1 为设计目标，需分阶段实现。

## 十二、总体评价

这条思路在“代码生成 + 高危工具调用”这个窄场景里，实际潜力很高。  
它解决的是自回归模型“无回头路 + 错误上下文向下游扩散”两个真实结构缺陷，代价需要实测，边界需要写清。  
它不能提升模型基础智能，不能保证逻辑正确，不能替代外部验证，但能显著减少“手贱炸环境”和“被错误 Token 拖累”这两类问题。

**关于从编辑点重算的补充定位**：  
已有研究指出，简单编辑 KV cache 可能导致时间混乱——后续 token 的 KV 对仍反映编辑前状态。本机制的做法是从编辑点开始重算，使编辑点之后的 KV cache / 前缀缓存失效并重新计算。  
但该研究的适用范围比 v3.1 描述的更窄，全量重算是保证一致性的基准实现，不是唯一方案，其成本必须测量。  
在本地推理中可控制 KV cache；在托管 API 中应表述为“使编辑点之后的前缀缓存失效并重新 prefill”。  
代价是编辑点之后的缓存失效并需要重算，但换来的是语义一致性——是否值得，应由基准测试结果决定。

最大的剩余不足是：自审能力仍部分依赖模型自身；第三方无缓存 LLM 完整审核成本过高，当前只能靠自审与独立审核 Agent 的组合折中。  
如果厂商在训练阶段引入类似流程，它可能成为 Agent Runtime 的标准层。

一句话：  
**值得做，定位要准——它是执行前审查层和可编辑工作记忆，不是万能后悔药；下一步先用 MVP 验证提交与重算流程，再用长任务对比成功率、后续输入长度和延迟。**
