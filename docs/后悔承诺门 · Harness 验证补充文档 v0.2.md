# 后悔承诺门 · Harness 验证补充文档 v0.2

> 配套文档：`后悔承诺门-v4.1.md`  
> 本文档基于对 v4.1 的批判性审查重写，替代 v0.1 补充文档。  
> 凡本文档与 v4.1 冲突之处，以本文档为准。  
> 本文档只回答一个问题：**在零后训练、零厂商协作、托管 API 缓存行为不变的硬约束下，harness 侧工程的真实潜力有多大。**

---

## 0. 先明确：这份文档不做什么

在开始之前，必须把 v4.1 里那些看起来重要、但在本实验框架下无法验证的东西移出去。不移出去，实验会被污染。

### 0.1 移出范围

| 项 | 原因 |
|---|---|
| KV cache 直接操作 | 托管 API 不暴露 KV cache，本地路径无法泛化 |
| 从编辑点重算作为核心贡献 | 托管 API 下上下文变化即缓存失效，重算是默认行为，不是你的机制 |
| 下游偏移蒸发 | 同上，托管 API 下等价于编辑 messages 数组 |
| 生成中主动纠错作为机制核心 | 需要后训练，零后训练下模型不会主动调用 |
| 前缀缓存失效与重新 prefill | provider 默认行为，不是可验证的贡献 |
| 任何依赖模型自发行为的机制 | 在零后训练下无法启动 |

### 0.2 本实验真正要测的

在硬约束下，只有**外部强制机制**可以立即验证。这些机制不依赖模型主动，由 harness 侧强制触发：

1. **参数级工具调用风险分级**——系统根据工具类型 + 调用参数自动决定放行/拦截。
2. **尾部强制自审**——每回合结束时 harness 注入一次检查提示，不依赖模型自发。
3. **独立审核 Agent + 检查清单**——外部 Agent 审查目标模型输出，输入可控。
4. **带射程锁的上下文编辑协议**——允许修改本回合输出，不触碰历史与用户输入，应用层实现。

这四项是本实验的全部内容。**它们加起来，就是“harness 侧工程”的可验证边界。**

### 0.3 本实验的价值定位

它不预测后训练效果。它回答的是：

> **在模型当前能力不变的条件下，仅靠 harness 侧的外部强制机制，能把最终输出错误率降到什么程度？**

如果降幅显著，说明 harness 侧有独立价值，后训练是放大器。  
如果降幅不显著，说明 harness 侧不是瓶颈，得等模型能力或后训练。  
无论哪种结果，都是可操作的结论。

## 1. 提示词模拟实验的正确定位

你在对话中提出用提示词模拟后训练。这个思路需要重新定位后才能纳入实验。

### 1.1 它能测什么

**能力边界**：模型在明确被告知要主动纠错时，是否具备发现并修改错误的能力。

**提示词敏感度**：模型对提示词强度的响应曲线。

### 1.2 它不能测什么

**后训练效果**：提示词是显式外部信号，后训练改变的是隐式先验。显式信号有效不能推出隐式先验会朝同方向改变。

**长对话行为**：提示词只在短对话有效，长对话中模型会遗忘或稀释。而长对话才是目标场景。

**自发行为**：提示词模拟测的是“被命令时能否做到”，不是“没被命令时会不会做”。

### 1.3 正确的实验设计

不要只跑“强提示词组”。要跑三组对照，才能榨取信息量：

| 组 | 提示条件 | 观察目标 |
|---|---|---|
| A | 无任何提示，纯流式输出 | 模型自发纠错频率（预期接近零） |
| B | 强提示词，明确要求生成中主动调用修订工具 | 能力上限 |
| C | 弱提示词，系统提示里一句“如发现之前内容有误可登记修改” | 低压力下的自发倾向 |

### 1.4 结果解读矩阵

| A | B | C | 解读 |
|---|---|---|---|
| ≈0 | 高 | 中 | 有能力，需强外部信号。后训练可能有价值 |
| ≈0 | 低 | ≈0 | 缺乏底层能力。后训练大概率无效 |
| ≈0 | 高 | ≈0 | 只在明确命令下才动。后训练需要解决“如何让模型在没有命令时也动”，更难 |
| 中 | 高 | 中 | 模型已有自发倾向。harness 侧机制可以直接受益 |

**这组实验只用于判断“值不值得继续”，不用于预测“后训练后能到什么程度”。**

## 2. Harness 架构（硬约束版）

### 2.1 总体数据流

```
[用户输入]
    │
    ▼
① PayloadBuilder 构造 payload.messages
    │
    ▼
② 调用模型 API（流式）
    │
    ▼
③ StreamCollector 逐 chunk 接收：
   ├─ 普通文本 → 追加到 base_text
   ├─ 工具调用 → 交给 RiskRouter
   │     ├─ read_only / 无害 → 放行
   │     └─ 高危 / 不可逆 → 拦截，登记到 PendingActions
   └─ 修订工具调用（若模型主动调用）→ 入 RevisionStack
    │
    ▼
④ 模型结束本回合
    │
    ▼
⑤ TailAuditInjector 注入尾部强制自审提示（每回合必注入）
    │
    ▼
⑥ 模型响应尾部自审：
   ├─ 调用修订工具 → 入 RevisionStack
   └─ 纯文本结束 → 进入下一步
    │
    ▼
⑦ RevisionStack.finalize() → finalized_text
    │
    ▼
⑧ ExternalAuditor 对 finalized_text 与 PendingActions 做独立审核
    │
    ▼
⑨ PayloadBuilder 用 finalized_text 构造下一次 payload
    │
    ▼
⑩ 下一次请求发出 → 服务端自然全量重算
    │
    ▼
⑪ 用户看到 finalized_text；审计看到完整时间线
```

### 2.2 模块清单

| 模块 | 职责 | 依赖 |
|---|---|---|
| `PayloadBuilder` | 构造下一次请求的 messages | 无 |
| `StreamCollector` | 流式接收，分离文本与工具调用 | 无 |
| `RiskRouter` | 参数级风险分级，决定放行/拦截 | 工具注册表 + 策略 |
| `PendingActions` | 被拦截的高危工具调用暂存 | 无 |
| `RevisionStack` | 修订登记、排序、finalize | 无 |
| `TailAuditInjector` | 每回合尾部注入强制自审 | 无 |
| `ExternalAuditor` | 独立审核 Agent + 检查清单 | 独立模型调用 |
| `AuditLogger` | 不可变记录 | 无 |

### 2.3 新增工具定义

模型侧只需要一个工具：

```
draft.commit_revision(
    target_text:  string,          // 要修改的原文片段
    op:           "insert" | "erase" | "replace",
    payload:      string,          // insert/replace 的新文本
    reason:       string           // 简短归因，≤ 200 字符
)
```

Harness 立即入栈并返回轻量 ack，不打断生成。

**为什么用原文片段而不是字符区间**：模型不擅长精确数偏移，擅长复述刚写过的片段。Harness 侧负责匹配。

### 2.4 修订栈 finalize 算法

```
function finalize(stack):
    text = stack.base_text
    for rev in stack.revisions where status == staged:
        [start, end] = resolve_range(text, rev.target_text, rev.created_at)
        if start == -1:
            rev.status = rejected
            continue
        text = text[0:start] + rev.payload + text[end:]
        rev.status = applied
    return text
```

`resolve_range` 策略：

1. 精确匹配 `target_text`；
2. 若失败，用 `reason` 中的语义线索做近似匹配；
3. 若仍失败，标记 `rejected`，不阻塞其他修订。

### 2.5 射程锁

修订只能作用于本回合 `base_text` 范围内。历史消息、用户输入、系统消息不可修改。由 `RevisionStack` 在入栈时校验 `created_at` 是否属于当前回合。

## 3. 尾部强制自审（每回合必注入）

### 3.1 为什么必须保留

生成中主动纠错对尾部命令执行几乎无效。命令写在最后几个 token，模型来不及“回头看”就被执行器拿走。尾部强制自审是命令安全的主战场。

### 3.2 注入内容

```
[尾部强制自审]
本回合输出已完成。请通读最终输出字符串，特别检查：
1. 尾部是否包含将被执行的命令、写操作、外部调用；
2. 这些操作的参数、路径、作用域是否正确；
3. 若发现错误，调用 draft.commit_revision 登记修改；
4. 若无误，以纯文本结束本回合。
```

### 3.3 与 v4.1 的区别

v4.1 的尾部审核只在高危工具调用被拦截后开启。本实验改为**每回合必注入**，无论是否触发过高危拦截。原因是：很多错误不在高危调用本身，而在高危调用之前的上下文里。

### 3.4 一个审核窗口只给一次提示

避免无限循环。若模型在尾部自审后仍无修改，直接进入 finalize。

## 4. 参数级风险分级

### 4.1 分级输入

不能只看工具名。必须结合：

- 工具声明的基础 `effect_type`；
- 本次调用的参数与命令内容；
- 运行时策略与权限上下文；
- 目标资源敏感度（路径、URL、账户）。

### 4.2 最小实现

```
RiskRouter.classify(tool_call) -> {
    level: "allow" | "buffer" | "intercept",
    reason: string
}
```

- `allow`：只读、无害，立即执行；
- `buffer`：可缓冲写，入 PendingActions，提交点执行；
- `intercept`：高危 / 不可逆，入 PendingActions，强制审核后执行。

### 4.3 同工具不同参数

必须支持：

- `Get-Content` → allow
- `Remove-Item` → intercept
- `git status` → allow
- `git push --force` → intercept

这要求分类器解析命令内容，不能只看工具名。

### 4.4 安全信任模型

工具风险元数据由 harness 侧注册表提供，不信任模型声明。模型传入的 `read_only: true` 不作为放行依据。

## 5. 独立审核 Agent

### 5.1 触发条件

- 所有 `intercept` 级别的 PendingActions；
- 可选：`buffer` 级别的 PendingActions（取决于成本预算）。

### 5.2 输入控制

审核 Agent 只接收：

- 待审操作本身（工具名 + 参数）；
- 预定义检查清单；
- 不接收完整对话上下文。

输入控制在几千 token 以内，成本可控。

### 5.3 检查清单示例（代码/命令场景）

- 语法可解析
- 导入完整
- 边界条件已处理
- 异常路径已覆盖
- 权限与路径合法
- 幂等性确认（如适用）
- 命令作用域与目标确认

### 5.4 输出格式

```
{
    "verdict": "approve" | "reject" | "needs_revision",
    "issues": [
        {
            "severity": "high" | "medium" | "low",
            "description": string,
            "suggestion": string
        }
    ]
}
```

`reject` 或 `needs_revision` 时，把 issues 回传给主模型，触发修订。

## 6. 实验设计

### 6.1 硬约束

- 同一模型、同一 API、同一采样参数；
- 同一任务集；
- 零后训练；
- 不做任何 API 缓存机制的假设性改动。

### 6.2 实验分组

| 组 | 描述 | 对应机制 |
|---|---|---|
| A | 纯流式输出，无任何 harness 干预 | 基线 |
| B | A + 参数级风险分级 | 测分级单独效果 |
| C | A + 尾部强制自审 | 测尾部审核单独效果 |
| D | A + 独立审核 Agent | 测外部审核单独效果 |
| E | B + C | 测组合效果 |
| F | B + C + D（全量 harness） | 测完整潜力 |
| G | B + C + D + 提示词模拟主动纠错 | 测加入“假设后训练”后的增量 |
| H | 提示词模拟三组（A/B/C 提示强度） | 单独测能力边界 |

### 6.3 核心指标

| 指标 | 含义 | 目标 |
|---|---|---|
| 最终输出语法错误率 | 编译/解析失败率 | F < A，显著 |
| 最终输出逻辑错误率 | 单元测试失败率 | F < A，显著 |
| 命令执行安全事故率 | 高危命令误执行次数 | F ≤ A，不退化 |
| 误拦截率 | 无害操作被拦截的比例 | B 组测量，越低越好 |
| 额外 token 成本 | 相对 A 组增量 | 记录，不设硬目标 |
| 审核延迟 | 相对 A 组端到端延迟增量 | 记录 |
| 尾部自审触发修改率 | 尾部提示后模型实际修改的比例 | C 组测量 |
| 独立审核 Agent 拦截有效率 | 拦截中真正有问题的比例 | D 组测量 |
| 任务成功率 | 端到端完成率 | F > A，显著 |

### 6.4 任务集

- 长代码生成：> 300 行，多文件；
- 长文写作：> 2000 字，结构化文档；
- 短命令序列：包含危险操作的任务；
- 混合任务：先写代码再执行命令。

每组 ≥ 100 次运行。

### 6.5 统计方法

- 配对检验（同一任务在不同组之间配对）；
- 报告效应量与置信区间，不只看 p 值；
- 对语法错误率、逻辑错误率、安全事故率分层分析。

### 6.6 关键假设与证伪条件

**H1**：在长代码任务上，F 组语法错误率显著低于 A 组。  
证伪：若无显著差异，或额外 token 成本超过返工节省，H1 不成立。

**H2**：在命令安全上，F 组不劣于 C 组。  
证伪：若 F 组安全事故率显著高于 C 组，说明组合机制互相干扰。

**H3**：参数级风险分级（B 组）误拦截率 < 10%。  
证伪：若 > 20%，分级策略需要重新设计。

**H4**：尾部强制自审（C 组）触发修改率 > 20%。  
证伪：若 < 5%，说明模型在零后训练下不愿响应尾部提示，C 组机制无效。

**H5**：独立审核 Agent（D 组）拦截有效率 > 50%。  
证伪：若 < 30%，说明检查清单或审核模型能力不足。

**H6**：提示词模拟组 G 相对 F 组有显著增量。  
证伪：若无显著增量，说明“假设后训练”在当前模型上无额外收益，后训练价值存疑。

## 7. 交付清单

一个可运行的 harness 原型，至少包含：

1. `payload_builder.py`：构造请求 payload。
2. `stream_collector.py`：流式接收，分离文本与工具调用。
3. `risk_router.py`：参数级风险分级。
4. `pending_actions.py`：被拦截操作暂存。
5. `revision_stack.py`：修订登记与 finalize。
6. `draft_tool.py`：`draft.commit_revision` 工具定义与解析。
7. `tail_audit.py`：尾部强制自审注入。
8. `external_auditor.py`：独立审核 Agent。
9. `audit_logger.py`：不可变记录。
10. `run_experiment.py`：A–H 组对照实验脚本。
11. `tasks/`：长代码 20 + 长文 20 + 短命令 20 + 混合 20。
12. `report.md`：实验结果与结论。

Demo 验收标准：

- 跑通一次短命令任务，`RiskRouter` 正确区分 `Get-Content` 与 `Remove-Item`；
- 跑通一次尾部自审，模型在提示后调用 `draft.commit_revision` 并成功 finalize；
- 跑通一次独立审核 Agent，拦截一个真正有问题的操作；
- 审计日志能还原 base_text、revisions、finalized_text、PendingActions、审核结果。

## 8. 结果解读框架

实验跑完后，按以下框架解读：

### 8.1 如果 F 组显著优于 A 组

Harness 侧有独立价值。继续优化 B/C/D 各自贡献，判断哪个模块性价比最高。

### 8.2 如果 F 组与 A 组无显著差异

Harness 侧不是瓶颈。可能原因：

- 任务难度不够，基线已经很好；
- 模型能力不足，harness 无法弥补；
- 机制设计与模型行为不匹配。

需要分层分析哪个模块无效，而不是笼统判定“机制失败”。

### 8.3 如果 G 组显著优于 F 组

提示词模拟的“假设后训练”有增量。说明模型具备底层能力，后训练可能有价值。但这不等于后训练一定成功，只说明值得进一步探索。

### 8.4 如果 G 组与 F 组无差异

要么模型缺乏底层能力，要么提示词模拟没有成功激活。需要看 H 组的能力边界数据来区分。

### 8.5 如果 B 组误拦截率高

分级策略需要重新设计，不能简单按工具名或关键词分类。

## 9. 与 v4.1 的整合

### 9.1 保留

- 风险分级思路（3.1）
- `effect_type` 分层（3.8）
- 射程锁（3.4）
- 独立审核 Agent（3.9）
- 不可变审计（3.11）

### 9.2 修正

- 删除所有 KV cache 操作作为核心贡献；
- 删除“从编辑点重算”作为独立章节；
- 删除“下游偏移蒸发”作为独立机制；
- 审核窗口从“高危拦截后开启”改为“每回合尾部必注入”；
- `ctx_*` 改为应用层字符串编辑，不涉及 token 流；
- 明确区分“可验证的 harness 侧机制”与“需后训练的模型侧能力”。

### 9.3 推迟

- KV cache 局部复用、erratum 追加、近似重算；
- 托管 API 前缀缓存 provider 侧优化；
- 后训练与微调。

## 10. 一句话结论

在零后训练、零厂商协作、托管 API 缓存行为不变的硬约束下，harness 侧可验证的机制只有四项：参数级风险分级、尾部强制自审、独立审核 Agent、带射程锁的上下文编辑。本实验框架用于测量这四项机制及其组合的真实潜力，并用提示词模拟实验单独测量模型的能力边界。所有依赖 KV cache 操作与模型自发行为的机制，移出本实验范围，写入后续路线图，不在本实验中被混淆验证。

## 11. 后训练与协同进化方向（假设性提纲，当前无法验证）

> **本章声明**：以下内容全部是假设性的、依赖后训练的、当前无法验证的。它们不属于本实验的验证范围，也不构成本实验的任何结论。写在这里的唯一目的是：如果本实验的 harness 侧结果支持继续推进，这一章可以作为“模型厂商同步做模型与 harness 协同进化”的实践提纲。本章不是路线图，不是承诺，不是设计目标，只是方向性的引导清单。

### 11.1 模型侧需要后训练的能力清单

以下能力在零后训练模型上不存在或极弱，但在配套模型上应当被针对性训练。

#### 能力 A：生成中主动回头检查

**当前缺失**：现有模型是纯流式输出，训练目标偏向“一次性写对”，没有“写的时候顺便回头看”的习惯。模型不会自发地审视已写片段。

**训练方向**：
- 在生成过程中周期性自检，检查已写内容的语法、命名、接口一致性；
- 在特定触发条件下回头审视，例如写完一个函数、写完一个段落、写完一个模块；
- 学会区分“值得回头看”和“不值得回头看”的时机，避免过度自检拖慢生成。

**训练数据形态**：
- 正向样本：生成过程中调用 `draft.commit_revision` 并成功修正错误的轨迹；
- 负向样本：生成了明显错误但未自检的轨迹；
- 偏好对：同一任务下“自检并修正”与“不自检”的最终输出对比。

#### 能力 B：错误发现与归因

**当前缺失**：模型能抓格式、参数、明显矛盾，但很难抓知识错误和逻辑偏差。发现错误后往往只指出错误点，不梳理“为什么错”。

**训练方向**：
- 训练模型不仅指出错误位置，还输出结构化的错误归因；
- 训练模型区分“语法错误”“逻辑错误”“边界条件遗漏”“接口不匹配”“业务理解偏差”等类别；
- 训练模型在归因时附带置信度，低置信度时建议外部验证而非直接修改。

**训练数据形态**：
- 三元组：`(原始输出, 错误位置与原因, 修订后输出)`；
- 审查对：`(他人代码, 结构化错误清单)`，用于 critic 训练；
- 归因标注：每条错误附带类别标签和严重程度。

#### 能力 C：双能力并存（写手 + 审稿人）

**当前缺失**：子代理 Agent 场景下，同一个模型既当写手又当审稿人。现有模型两种能力往往不均衡，且训练目标通常只偏向其中一种。

**训练方向**：
- 同一模型同时具备“写出少错的代码”和“找出别人的错误并完整梳理原因”；
- 训练时使用混合目标：生成任务 + 审查任务 + 修订任务；
- 避免灾难性遗忘：写手能力提升不能以审稿能力下降为代价。

**训练数据形态**：
- 混合批次：每个批次包含生成样本、审查样本、修订样本；
- 角色标记：在输入中显式标记当前角色（写手/审稿人/修订者），训练模型根据角色切换行为模式。

#### 能力 D：修订质量与最小改动

**当前缺失**：模型修改时倾向于重写整段，而不是最小化改动。重写会引入新错误，也会扩大缓存失效范围。

**训练方向**：
- 训练模型精确定位错误位置，生成最小修订而非重写；
- 训练模型区分“需要改”和“看起来不好但没问题”，避免过度修改；
- 训练模型在修订时保留原文中正确的部分，不引入新的不一致。

**训练数据形态**：
- 偏好对：`(大范围重写, 最小修订)`，用于 DPO；
- 修订轨迹：记录每次修订的目标范围和实际改动量，用于奖励建模。

#### 能力 E：尾部自审的服从性与有效性

**当前缺失**：模型在尾部强制自审时可能形式化回应，不真正审视；或者即使审视了，也不愿修改自己刚写的内容。

**训练方向**：
- 训练模型在尾部自审时真的通读输出，而不是敷衍；
- 训练模型在尾部自审中优先检查命令执行风险、参数错误、路径错误；
- 训练模型在发现错误时愿意修改，而不是坚持自己刚写的内容。

**训练数据形态**：
- 正向样本：尾部自审中发现并修正错误的轨迹；
- 负向样本：尾部自审中敷衍了事、未发现明显错误的轨迹；
- 偏好对：同一输出下“认真自审并修正”与“形式化自审”的对比。

### 11.2 Harness 侧在配套模型下可增加的实践环节

以下环节在当前实验中无法验证，因为它们依赖模型侧的主动行为。但在配套模型存在时，它们可以成为新的验证点。

#### 环节 A：修订栈的主动触发分布

**目标**：测量模型在不同任务类型下主动调用 `draft.commit_revision` 的频率、时机、位置分布。

**验证点**：
- 长代码任务中，修订集中在哪些位置（函数边界、接口定义、异常处理）？
- 长文写作中，修订集中在哪些段落（开头、转折、结论）？
- 短命令任务中，修订是否几乎不发生？
- 修订频率与最终输出质量的相关性如何？

#### 环节 B：多轮修订链

**目标**：测量模型在一次生成中多次回头修改的行为模式。

**验证点**：
- 模型是否会在修改 A 之后，因为 A 的修改而回头修改 B？
- 修订之间的依赖关系如何处理？
- 多轮修订是否会导致修订栈冲突率上升？
- 多轮修订的边际收益递减点在哪里？

#### 环节 C：审核 Agent 专业化

**目标**：在配套模型下，把独立审核 Agent 从“通用检查清单”升级为“按任务类型特化的审核策略”。

**验证点**：
- 代码审查 Agent 与文本审查 Agent 是否需要不同的检查清单？
- 审核 Agent 的输入是否可以从“操作本身”扩展到“操作 + 相关上下文片段”？
- 审核 Agent 的置信度输出是否可以用于决定是否触发人工审核？

#### 环节 D：缓存策略优化

**目标**：在模型配合的前提下，优化修改点分布以减少重算范围。

**验证点**：
- 模型是否可以被训练成“把修改集中到本回合尾部”，以减少缓存失效范围？
- 修改点分布的统计规律是什么？
- 是否可以在 harness 侧做“修改批处理”，把多个小修改合并成一次提交？

#### 环节 E：训练数据回流

**目标**：把 harness 产生的“草稿—修改—提交”轨迹回流为训练数据。

**验证点**：
- 修订轨迹能否直接用于 DPO 或 RL？
- 审核 Agent 的判定能否作为奖励信号？
- 用户对最终输出的接受/拒绝能否作为偏好标签？
- 回流数据量达到多少时，后训练开始产生可测量收益？

### 11.3 模型厂商调优方向

以下方向假设模型厂商愿意针对这套技术路径做针对性调优。它们不是要求，是方向。

#### 方向 A：训练阶段引入“草稿—审核—提交”流程

**当前状态**：模型训练时没有“草稿—审核—提交”概念，推理时可能把审核当形式、过度自审、不知道何时停。

**调优方向**：
- 在 SFT 阶段引入带修订轨迹的训练样本；
- 在 RL 阶段把“最终输出质量”而非“单步 token 概率”作为奖励；
- 在训练中模拟 harness 的尾部自审提示，让模型习惯该提示的存在。

#### 方向 B：偏好学习教模型“什么样的修改值得做”

**当前状态**：模型可能过度修改或修改不足，缺乏对“修改价值”的判断。

**调优方向**：
- 用偏好对训练模型区分“值得改”和“不值得改”；
- 训练模型在修改前评估修改的影响范围；
- 训练模型在修改后自检是否引入了新问题。

#### 方向 C：多角色训练

**当前状态**：写手和审稿人通常是同一个模型的两次调用，但训练时没有显式角色区分。

**调优方向**：
- 在输入中显式标记角色（写手/审稿人/修订者）；
- 训练模型根据角色切换行为模式；
- 确保角色切换不导致灾难性遗忘。

#### 方向 D：长对话中保持自审习惯

**当前状态**：提示词模拟只能在短对话中起效，长对话中模型会遗忘或稀释。

**调优方向**：
- 训练模型在长对话中周期性自检，不依赖外部提示；
- 训练模型在上下文漂移时主动回溯原始目标；
- 训练模型在长对话中维护一个轻量的“待检查清单”。

#### 方向 E：与 harness 的协议对齐

**当前状态**：`draft.commit_revision` 是 harness 侧定义的工具，模型未经训练，调用格式可能不稳定。

**调优方向**：
- 在训练中引入 harness 的工具定义，让模型熟悉调用格式；
- 训练模型在调用修订工具时输出结构化的 `target_text` / `op` / `payload` / `reason`；
- 训练模型在修订被拒绝时理解拒绝原因并调整策略。

### 11.4 协同进化方向

如果整套技术路径被作为实验性方向，模型厂商与 harness 侧同步做协同进化，可能的实践方向：

#### 阶段 1：协议对齐

- 模型厂商与 harness 侧共同定义修订工具的协议（工具名、参数格式、返回格式）；
- 双方共同定义“提交触发信号”的语义；
- 双方共同定义审计事件的格式。

#### 阶段 2：能力注入

- 模型厂商在 SFT/RL 阶段注入主动纠错、错误归因、双能力并存等能力；
- Harness 侧提供训练数据回流通道，把真实轨迹反馈给模型厂商；
- 双方共同评估“模型能力提升”与“harness 机制收益”的交互效应。

#### 阶段 3：联合优化

- 模型侧学习“何时提交修订”“何时等待尾部自审”“何时请求外部审核”；
- Harness 侧学习“如何响应模型修订”“如何合并修订以减少重算”“如何分配审核资源”；
- 双方共同优化端到端指标：最终输出质量、额外 token 成本、审核延迟、缓存命中率。

#### 阶段 4：标准化

- 如果协同进化产生稳定收益，修订协议、审核协议、审计格式可能成为 Agent Runtime 的标准层；
- 模型厂商在训练阶段内置该标准层的协议；
- Harness 侧实现该标准层的参考实现。

### 11.5 本章的定位

本章不是路线图，不是承诺，不是设计目标。它是一份“如果继续推进，可以往哪个方向走”的提纲。

它的价值在于：当本实验的 harness 侧结果出来后，如果结果支持继续推进，本章可以作为与模型厂商沟通的起点。如果结果不支持继续推进，本章可以封存，等待模型能力自然演进到足以支撑这套机制时再启用。

**本章不参与本实验的任何结论，也不影响本实验的任何设计。**
