## 1. 先纠正一个常见误解：这不是"绕过重算"，而是"精确的部分重算"

**核心结论先说**：

> KV 手术**能省掉的是「重编码已存在的前缀」**，**不能省掉「重新生成新内容」**。
> 一切收益必须用"省下的 prefill 量 − 新增的 decode + 补偿重编码量"来算，
> **不能笼统说成"不用重算了所以快"**。

这条决定了后面所有成本分析。$6 节给精确公式。

## 2. 文献基础（每条都注明它解决了哪个工程问题）

### 2.1 最核心的一篇：PIE（与你的设想几乎同构）

**《Let the Code LLM Edit Itself When You Edit the Code》**，ICLR 2025
[论文页](https://proceedings.iclr.cc/paper_files/paper/2025/hash/9530635032b95cea9585bd800d308300-Abstract-Conference.html) · [PDF](http://arxiv.org/pdf/2407.03157v1)

**它做的事**：用户改了代码 → KV cache 里对应区间的条目失效 → 重算太贵。
PIE 的做法是**只重算被编辑的区间**，其余**分类复用**。

**它给出的编辑形式化（这是重点）**：

$$K^{\text{edit}} = \mathrm{Concat}\left(K_{[1:i]},\; K^{\text{edit}}_{[i+1:i+m]},\; K_{[i+m+1:\cdot]}\right)$$

**关键工程结论**：编辑后的 cache = **前缀（原样复用）** + **被编辑区间（重算）** + **后缀（复用但可能要调整位置）**。

**对你的直接意义**：
- 你说的"从修改开始点重新输出到结束点"= PIE 的**被编辑区间**。
- 你没说的、但必须处理的 = **后缀怎么办**（见 §3 缺陷 1）。
- PIE 还指出：**位置偏移（position offset）会让后缀的 KV 不再对齐**，这是主要误差来源。

### 2.2 位置编码与 KV 编辑：为什么不能直接拼接

**RoPE 的数学性质**（多篇文献共用此式）：

$$\mathrm{PE}_i(m)^\top \mathrm{PE}_i(n) = \cos\big((m-n)\,\theta_i\big)$$

即 **RoPE 只依赖相对位置差 $(m-n)$**。推论：

| 操作 | RoPE 后果 |
|---|---|
| 整段区间**等长**替换 | 后缀相对位置**不变** → 后缀 K **可原样复用** |
| **不等长**替换 / 删除 / 插入 | 后缀相对位置**全部改变** → 后缀 K **失效，必须重编码 RoPE** |
| 只改 V（值）不改位置 | **V 无位置编码** → V **永远可复用** |

**这是整个设计最重要的技术支点**：**K 受位置影响，V 不受**。手术时必须分开处理。

### 2.3 已有的"原地更新"研究

- **EQUIP: EQUivariant preserving In-Place updates for Efficient token pruning**，ACL 2026
  [PDF](https://aclanthology.org/2026.acl-long.1210.pdf)
  研究"新 token 的 KV 能否**就地写入**被淘汰 token 的槽位"。结论与做法对"槽位复用/不重分配"有直接参考价值。
- **CachePrune: Teaching LLMs What Not to Follow via KV-Cache Editing**，ACL 2026
  [论文页](https://aclanthology.org/2026.acl-long.70/)
  **把 KV 编辑当作控制手段**（不只是省算力）。这为"用 KV 编辑塑造模型行为"提供了先例——正是你的动机。
- **Models Take Notes at Prefill: KV Cache Can Be Editable and Composable**
  [PDF](https://browse-export.arxiv.org/pdf/2606.17107)
  论证 KV cache **可编辑、可组合**，并给出"笔记（note）主导"的观察：**下游只移动 0.19–0.32**，说明编辑的影响范围**局部可控**——支持"只重编码受影响后缀"的做法。

## 3. 逐条纠错：你的设计里的问题

> 严重度：🔴 会直接导致方案失败 · 🟠 会导致结果错误 · 🟡 会导致工程返工

### 🔴 缺陷 1：假定"修改点之后全部复用"——不等长修改时这是错的

**你的原文**：
> 服务器端当轮对话的 KV：`[1010111111111111010101010101010]`（这是修改后的版本，丢弃修改过程不存）

**问题**：你的例子里替换段与原文**等长**（`01010101010` 10 位 → `111111111111` 12 位，其实**不等长**，见缺陷 4）。
一旦替换段长度 ≠ 原段长度，**其后所有 token 的位置整体平移**，而 **K 里已烘焙了 RoPE**。

因为 $\mathrm{PE}(m)^\top\mathrm{PE}(n)=\cos((m-n)\theta)$，K 向量**只对"当时的位置"有效**。位置平移后：

- **V：可以原样复用**（无位置编码）✅
- **K：必须重编码 RoPE**，否则注意力分数全错 ❌

**你漏掉的就是这一句**：不是"拼接"，而是"**拼接 + 后缀 K 重编码**"。

**好消息（我已核实）**：你的运行框架**已经内置了这个补偿**：

```
include/llama.h L920-931
// Adds relative position "delta" to all tokens ... in [p0, p1)
// If the KV cache is RoPEd, the KV data is updated accordingly:
//   - lazily on next llama_decode()
//   - explicitly with llama_kv_cache_update()
LLAMA_API void llama_kv_cache_seq_add(ctx, seq_id, p0, p1, delta);
```

**所以正确做法是**：
```
1. llama_kv_cache_seq_rm(ctx, seq, span_start, span_end)      // 删旧区间
2. 在 span_start 处 decode 新 token 序列                        // 只算新区间
3. llama_kv_cache_seq_add(ctx, seq, 新段末, +∞, delta)         // 后缀位置补偿
4. llama_kv_cache_update(ctx)                                  // 显式落定
5. llama_kv_cache_defrag(ctx)                                  // 可选，整理碎片
```
**第 3 步你完全没提，缺了它后缀就是错的。**

### 🔴 缺陷 2：客户端存"字符串"、下轮用字符串当请求头 → 分词不一致，对账必然失败

**你的原文**：
> 客户端中存储的字符串：`[1010111111111111010101010101010]`

**问题**：BPE/BBPE 分词**不可逆**。你拼接出的字符串 `...1010111111111111010101010101010...`
在**下一次请求重新分词**时，边界会跑到**不同的位置**，产生与服务器 KV 不对应的 token 序列。

举例（真实会发生）：
```
原始生成 token:  ["def", " foo", "(x)", ":"]     → 4 个 token
替换中间后字符串: "def bar(x):"
重新分词结果:    ["def", " bar", "(x):"]        → 3 个 token  ← 对不上了
```
**服务器 KV 是 4 槽，客户端说是 3 个 token → 前缀头对不上 → 整个机制崩掉。**

**修正**：
- **不要存字符串作为权威**。权威必须是 **token id 序列**。
- 客户端存 `Tuple[token_id, ...]`（以及用于显示的字符串，但**字符串不是权威**）。
- 下轮请求走**扩展协议**，把 token id 序列**显式传给服务端**，**不要让它重新分词**。
- 利用已有的 `/tokenize` 端点把"模型给出的文本片段"映射成 token 区间：

```
examples/server/server.cpp L1486
const auto handle_tokenize = ...    // 返回 token id 数组
const auto handle_detokenize = ...  // token id → 文本（仅用于显示）
```

**这条如果做错，对整个方案是致命的，因为它不可调试**（表现为"偶尔对不上，偶尔又能对上"）。

### 🔴 缺陷 3：修改过程产生的 KV 会污染后续生成 → 必须"回滚 + 只补算新区间"

**你的原文**：
> 丢弃修改过程产生的修改工具 KV 缓存和 harness 端的字符串也是请求头部分，最后双方手里的应该是……

**你说要"丢弃"，但没说清怎么丢。** 这里有个隐蔽的坑：

如果替换内容是"模型在**带着全部旧 KV** 的上下文里生成的"，那么新 token 的 K/V 是在**能看到被替换掉的坏内容**的条件下算出来的。于是：

- 你 `seq_rm` 掉旧区间 → 但**新内容的 KV 是在"旧内容还在"时算的**
- 这违反 PIE 的 $K^{\text{edit}}_{[i+1:i+m]}$ —— 编辑区间的 K **必须在"编辑后的上下文"里**算

**换句话说**：新内容必须**在删掉旧内容之后再算**，否则它承载了本应被删除的信息。这正是 v4.1 讲的"时间混乱"。

**正确流程（严格顺序，不可调换）**：
```
① 模型发起 KV 修改工具调用（此时它的 KV 里含旧内容）
② 记录 span_start / span_end / op
③ llama_kv_cache_seq_rm(span_start, span_end)        ← 先删，把坏内容从 cache 里彻底去掉
④ 在 span_start 处 decode 新 token 序列              ← 在"干净上下文"里算新 KV
⑤ 后缀位置补偿 seq_add + update
⑥ 丢弃"生成修改工具调用本身"那一小段 KV
```
**③ 必须在 ④ 之前。** 你的描述里没有明确这个顺序，后接手的 Agent 极可能写反。

### 🟠 缺陷 4：你的替换示例自身不等长，暴露了长度语义没定义

**你的原文**：
> 原始：`[1010` **`01010101010`** `010101010101010]`
> 替换内容：`[` **`111111111111`** `（长度可自定义）]`

被替换段 **11 位**，替换内容 **12 位**，**不等长**。而你在"最终结果"里写：

```
[1010111111111111010101010101010]
```
前缀 `1010` + 12 位 + 后缀 `010101010101010`(15 位) = 3 + 12 + 15 = 30 位，
原文 = 3 + 11 + 15 = 29 位。**长度对不上**（30 vs 29）。

**问题**：你没定义"替换是否允许变长"，却给了变长的例子和不变长的结果。

**必须写死**：

| 语义 | 是否允许变长 | 后缀代价 |
|---|---|---|
| `replace_equal_len` | 严格等长（长度不符 → 拒绝） | 0（后缀可原样复用）✅ 最安全 |
| `replace_resize` | 允许变长 | 后缀 K 需 RoPE 重编码（`seq_add`） |

**建议**：**v1 只实现 `replace_equal_len`**，把变长留到 v2。理由：等长替换时**后缀完全无需补偿**，正确性最容易保证，也最容易对账。等长是最常见的纠错场景（改一个标识符、改一个常量）。

**另外**：你的例子用 `0`/`1` 表示内容，但**一个 `0` 到底是一个 token 还是一个字符？** 必须明确：**所有区间一律以 token 为单位**（见 §3 缺陷 9）。

### 🟠 缺陷 5：把"对账"设成逐位相等，在浮点 + 量化下做不到

**你的原文**：
> 完成对账（保证双方手里的前缀头和 KV 缓存都是能对上的）

**问题**：KV 是浮点张量。即使同一份权重、同一个输入：

- **KV 量化**（你的启动脚本用 `-ctk q4_0 -ctv q4_0`）→ KV 本身是**有损**的，量化后再"对账"逐位相等无意义
- **批次/线程调度不同** → 浮点加法顺序不同 → **结果按位可能不同**
- **不同后端**（CUDA / CPU / Metal）→ 结果不同

**修正：把"对账"分成两层，分开定义**

| 层 | 对象 | 判据 |
|---|---|---|
| **L1 结构对账**（必须严格） | **token id 序列 + 每个 token 的位置 + 总长度** | **必须精确相等**。这是客户端与服务端真正的契约 |
| **L2 数值对账**（诊断用） | KV 张量字节 | **不要求相等**；记录 hash 用于**排查漂移**，并按 §3 缺陷 6 设容差 |

**实现**：用已有 API 做 L2 观测：
```c
llama_state_seq_get_size(ctx, seq, flags)              // 需要多少字节
llama_state_seq_get_data(ctx, dst, size, seq, flags)   // 导出该序列 KV
llama_state_seq_set_data(ctx, src, size, dst_seq, flags)// 回灌（调试/迁移用）
```

**L1 才是硬契约。** 把 L2 当成"必须相等"会导致无止境的假失败。

### 🟠 缺陷 6：「保留了为什么错的信息」这个假设，与你自己的流程矛盾

**你的原文**：
> 这样修改即清掉了坏 Token 对应的 KV 缓存由保留了为什么错的信息（因为替换部分实际上是有受到曾经坏 token 和坏 KV 导致的后续字段隐形 KV 向量影响积累的影响的，算是保留了为什么错的信息）

**这个推理有问题**。按 §3 缺陷 3 修正后的流程，**替换内容是在删掉旧 KV 之后算的**——那么：

- 新 token 的 K/V 在计算时**看不到坏内容**（这正是修复时间一致性的前提）
- 因此它**不隐含"为什么错"的信息**
- 它的 K/V 只表达"正确内容"，这是**feature 不是 bug**：正因如此时间才一致

**如果你真想保留"为什么错"**，不能靠 KV 隐式残留，必须**显式**：
- 把错误与归因写进**不可变审计日志**（`audit_logger`，已有）
- 或者由 harness 在后续 payload 里**显式注入**一句"此前此处曾误写为 X，已修正为 Y"

**建议**：**走显式路径**。隐式残留既不可控也不可测，还会让实验结论无法解释。

> 这一条不影响架构，但会影响**你怎么解释结果**。如果不澄清，接手 Agent 可能写出"验证错误信息保留度"这种无法测量的指标。

### 🟠 缺陷 7：中途纠错 vs "只在轮末改 KV" —— 你给了两个互斥的约束

**你的原文 A**：
> 框架侧模型运行时的流式输出方法不可改变（兼容现有模型格式）但是要在每轮结束后的 KV 缓存上做点文章（**当轮对话结束后才允许修改 KV**）

**你的原文 B**：
> 这些操作如果是由模型发起的主动纠错（用一样的格式）在模型纠错完后将这个纠错当做和结尾的纠错一样，**接下去仍然像正常流程一样从结尾开始让模型继续接下去生成**

**矛盾**：A 说"轮末才允许改"，B 说"中途改了之后继续生成"——中途改就**不是**轮末。

**而且这直接决定收益**（见 §6）：

| 方案 | 修改点位置 | 后缀长度 | 收益 |
|---|---|---|---|
| **A：只在轮末** | 输出末尾 | **后缀 = 0** | ⚠️ **省不到任何 prefill**（后缀为空，无重算可省） |
| **B：中途改后继续** | 输出中间 | 后缀可能很长 | ✅ **真正的收益来源**（省掉重生成后缀） |

**关键判断**：**你想验证的"收益"，几乎全部来自 B，而不是 A。** 但 B 需要一个你没定义的机制：

```
中途纠错的协议（必须定义）：
① 模型在流中发出 KV 修改工具调用
② 服务端识别到该工具调用 → 停止当前 decode（但保留已生成文本）
③ 应用手术（§3 缺陷 3 的 ③④⑤）
④ 从手术点继续 decode，直到模型自然结束
⑤ 客户端拿到"已修改 + 续写"的完整输出
```
**②"停止 decode"这一步改变了流式行为**（虽然你说的"流式输出方法不可改变"指的是**格式兼容**，但**时序上确实中断了**）。必须明确这算不算违反约束，或明确它是允许的例外。

**建议**：把"轮末手术"和"中途手术"当作**两个独立实验臂**分别实现和测量，不要混在一起。轮末臂虽然收益小，但**风险最低、最容易验证正确性**，适合做第一步。

### 🟡 缺陷 8：不要用近似注意力

文献里的 **APE**（自适应并行编码）用**近似注意力**换取速度。**本设计不要用**。

理由：你的实验目的是**验证机制收益**。引入近似 → 误差来源变成两个（机制 + 近似）→ **无法归因**。这正是 v0.2 §0「不移出去，实验会被污染」的同一种错误。

**明确写死：本设计的所有 KV 操作必须精确，禁止近似/插值/舍入式省算。**

### 🟡 缺陷 9：区间语义必须以 token 为单位定义，且注意半开区间

**必须写死**：

```
所有区间 = token 索引，0-based
所有区间 = 半开 [start, end)        ← 与 llama.cpp API 一致
空区间: start == end
禁止: end < start
越界: end > n_tokens → 拒绝整个操作（不截断）
```

**为什么强调半开**：你的描述用"包含开始点、包含结束点"（**闭区间**），而
`llama_kv_cache_seq_rm` 的定义是 **`[p0, p1)` 半开**：

```
include/llama.h L893
// Removes all tokens that belong to the specified sequence and have positions in [p0, p1)
```

**闭→半开是经典 off-by-one 来源。** 协议层就统一用半开，别在两层之间做转换。

---

### 🟡 缺陷 10：插入的"前/后"参数设计没有解决定位歧义

**你的原文**：
> 插入点（Token 定位点，真正的插入点和后面的前后参数一起得出）、前，后（这里增加前后主要是考虑到开头和末尾的追加，如果只让写一个插入点前后就被强行限定了）

**问题**：若 token 序列是 `[A, B]`，说"在 B 前插入"和"在 A 后插入"**是同一个位置**。`(定位点, 前/后)` 这种编码**对同一位置有两组不同参数** → 变成**非规范表示** → 对账时你以为不同、实际相同。

**修正（更简单且无歧义）**：**只用"插入点索引"表示"插入到该索引之前"**。

```
insert(pos, tokens):
  pos = 0          → 插到最前
  pos = n_tokens   → 追加到末尾
  0 < pos < n     → 插到 token[pos] 之前
```
- 开头、末尾都自然覆盖（`pos=0` / `pos=n`）→ **你担心的"被强行限定"并不存在**
- 每个位置**只有一种表示** → 无歧义

`insert(pos)` 在语义上 **完全等价于** `replace_equal_len(span=[pos,pos), new_tokens)`（空区间替换）。
**建议把三者统一成一个原语**，减少实现与测试面：

```
统一原语:  splice(start, end, new_tokens)
  replace: splice(i, j, T)    j > i
  delete : splice(i, j, [])   j > i
  insert : splice(p, p, T)    p == p
```
**v1 只实现这一个原语，对外暴露三种 op 只是语法糖。**

## 4. 统一原语与不变式

### 4.1 唯一原语

```
splice(seq_id, start, end, new_tokens) -> SpliceResult
    start, end : token 位置，0-based，半开 [start, end)
    new_tokens : token id 列表，可为空（= 删除）
```

| 对外 op | 等价调用 |
|---|---|
| `replace` | `splice(i, j, T)`，`j > i` |
| `erase` | `splice(i, j, [])`，`j > i` |
| `insert` | `splice(p, p, T)` |

### 4.2 必须永真的不变式（**逐条写成断言**）

```
INV-1  长度守恒（等长模式下）
       len(new_tokens) == (end - start)
       —— replace_equal_len 违反则拒绝整个操作

INV-2  前缀一致
       手术前 KV[0, start) 的 (token_id, position) 与手术后完全相同

INV-3  位置单调
       手术后 KV 中所有 position 严格递增、无空洞

INV-4  双端 token 一致（L1 对账）
       客户端 token 序列 == 服务端 KV 的 token 序列，逐位相等

INV-5  长度一致
       客户端 token 数 == 服务端 KV 占用槽位数

INV-6  轮末位置正确
       手术后 max(position) == 客户端 token 数 - 1

INV-7  历史不可变
       position < turn_start 的 KV 永不被 splice 触及
       （对齐现有 revision_stack 的射程锁语义）

INV-8  原子性
       splice 要么全部成功，要么 KV 完全不变；不允许半完成状态
```

**INV-8 特别重要**：C++ 侧做多步操作（rm → decode → seq_add → update），
**任何一步失败都必须回滚**。若无法回滚，必须**整轮作废并标记 `kv_op_failed`**，
**绝不能带着不一致的 KV 继续生成**（那会产出无法解释的结果）。

### 4.3 执行序列（写死顺序）

```
输入: seq_id, start, end, new_tokens, mode

1.  校验
    1.1 0 <= start <= end <= n_tokens
    1.2 mode == equal_len 时: len(new_tokens) == end - start
    1.3 start >= turn_start                        (INV-7)
    1.4 失败 → 返回 REJECT，KV 不动

2.  快照（用于回滚）
    2.1 用 llama_state_seq_get_data 导出该序列 KV 到内存缓冲
    2.2 记录 n_tokens_before

3.  删除旧区间
    llama_kv_cache_seq_rm(ctx, seq_id, start, end)      ← 必须先做（缺陷 3）
    失败 → 回滚

4.  计算新内容 KV（在"已删除"的干净上下文里）
    在 start 处 decode new_tokens
    失败 → 回滚

5.  后缀位置补偿
    delta = len(new_tokens) - (end - start)
    if delta != 0:
        llama_kv_cache_seq_add(ctx, seq_id, start + len(new_tokens), -1, delta)
    （等长模式下 delta == 0，此步跳过 —— 这也是 v1 选等长的原因）

6.  落定与整理
    llama_kv_cache_update(ctx)      // 让 K-shift / defrag 生效
    llama_kv_cache_defrag(ctx)      // 可选

7.  校验不变式
    INV-1..INV-7 逐条断言
    任一失败 → 回滚 + 标记 kv_op_failed

8.  返回
    {ok, n_tokens_after, kv_hash_l2, start, end, new_len}
```

**注意第 4 步的"干净上下文"**：`seq_rm` 只是把槽位标记为空闲，`decode` 新内容时
**不能**让新 token 看到已删除的内容。若实现上 `rm` 未立即生效，需先
`llama_kv_cache_update()` 再 `decode`。**这一点必须在原型阶段（HF DynamicCache）验证清楚。**

## 5. 协议设计（OpenAI 兼容扩展）

### 5.1 设计原则

| 原则 | 理由 |
|---|---|
| **新增旁路端点，不改 `chat/completions` 语义** | 你要求"流式输出方法不可改变、兼容现有模型格式" |
| 请求/响应携带 **token id**，不携带裸字符串 | 缺陷 2 |
| 区间一律 **半开、token 索引** | 缺陷 9 |
| 每个操作**幂等可查**：返回手术后的 L1 指纹 | 对账 |
| 失败必须**显式**返回错误码，禁止静默降级 | INV-8 |

### 5.2 端点

```
POST /kv/splice
{
  "seq_id": 0,
  "start": 128,            // token 索引，含
  "end": 133,              // token 索引，不含（半开）
  "new_tokens": [111,222], // token id；空数组 = 删除
  "mode": "equal_len",     // v1 仅支持 equal_len
  "request_id": "..."      // 幂等键

200 OK
{
  "ok": true,
  "n_tokens": 1024,                 // 手术后总长
  "prefix_token_ids": [ ... ],      // 用于 L1 对账（可分段/哈希）
  "l1_fingerprint": "sha256:...",   // hash(token_ids || positions)
  "kv_l2_hash": "sha256:...",       // 诊断用，不参与断言
  "applied": {"start":128,"end":133,"new_len":2}
}

409 Conflict   -> 幂等键重复但参数不同
422 Unprocessable -> 违反不变式（附 INV-x 编号）
500            -> 已回滚，附 kv_op_failed
```

**已有可参照范式**（`server.cpp`）：

```

```

### 5.3 工具定义（给模型看的那一层）

模型侧只看到**文本片段**，服务端负责映射到 token 区间：

```json
{
  "name": "draft.kv_splice",
  "arguments": {
    "op": "replace | erase | insert",
    "target_text": "被替换的原文片段（replace/erase 必填）",
    "anchor_text": "插入锚点原文片段（insert 必填）",
    "after": false,
    "new_text": "替换/插入的新文本"
  }
}
```

服务端处理：
```
1. /tokenize 把 target_text 映射为 token 区间 [start, end)
   —— 必须唯一匹配；多处匹配 → 拒绝（不做模糊匹配，对齐铁律/射程锁原则）
2. new_text → new_tokens（/tokenize）
3. mode=equal_len 时若 len 不等 → 拒绝并把实际长度回给模型让它重试
4. 执行 splice
5. 成功后把新的 target_text 对应文本回写客户端（客户端以 token id 为权威）
```

**为什么让模型给文本而不是 token id**：模型看不到 token 边界，强求 token id 不现实。
**但权威存储必须是 token id**——这个分工要写清楚，否则接手者会搞混。

## 6. 成本模型（必须按这个算，否则收益会被高估）

### 6.1 精确公式

设：
- $L_p$ = 前缀 token 数（手术点之前）
- $L_s$ = 被替换区间长度（= `end - start`）
- $L_n$ = 新内容长度（= `len(new_tokens)`）
- $L_{tail}$ = 后缀 token 数（**中途手术时 > 0；轮末手术时 = 0**）
- $c_{pre}$ = prefill 单 token 成本，$c_{dec}$ = decode 单 token 成本（$c_{pre} \gg c_{dec}$）

| 方案 | 成本 |
|---|---|
| **全量重算**（不用 KV 手术） | $L_p \cdot c_{pre} + (L_s + L_{tail}) \cdot c_{dec}$ |
| **KV 手术（等长）** | $L_n \cdot c_{dec}$（+ 补偿开销 ≈ 0） |
| **KV 手术（变长）** | $L_n \cdot c_{dec} + L_{tail} \cdot c_{K\text{-reencode}}$ |

其中 $c_{K\text{-reencode}}$ 是**只重编码 K 的 RoPE**（不是完整 forward），**远小于** $c_{pre}$。

### 6.2 三条必须记住的结论

**结论 1：手术省的永远是「$L_p \cdot c_{pre}$」这一项**（前缀不必重读）。
`seq_rm`+`seq_add` 让**前缀 KV 原样保留**，这才是真正的收益来源。

**结论 2：轮末手术（$L_{tail}=0$）省不到"后缀重生成"**，只省前缀。
所以**"轮末纠错"的收益上限是"一次 prefill"**，不是"半个输出"。

**结论 3：$L_n$ 必须真的产生**。替换内容由模型生成，**这部分 decode 成本无法避免**。
若 $L_n \approx L_s$，则**文本产出成本不变，只有 prefill 被省下**。

**推论（重要）**：
> 期望收益 ≈ $L_p \cdot c_{pre}$，与**输出长度无关，只与输入/上下文长度有关**。
> **上下文越长，收益越大；纯生成任务收益趋近于 0。**

**这解释了为什么"长代码任务"是主要受益场景**（长上下文 + 局部错误），
而"短命令任务"几乎无收益 —— 与 v0.2 §6.4 的任务分类正好对应。

### 6.3 成本项必须一起测

| 指标 | 定义 |
|---|---|
| `prefill_tokens_saved` | $L_p$（省下的 prefill token 数） |
| `decode_tokens_added` | $L_n$（新内容 decode） |
| `k_reencode_tokens` | 变长模式下的后缀 K 重编码量 |
| `ttft_delta` | 首 token 延迟变化 |
| `wallclock_delta` | 端到端墙钟变化 |
| `kv_op_overhead_ms` | 手术本身（含 defrag）耗时 |

**禁止只报"省了多少 token"而不报手术开销**——手术开销在小模型上可能吃掉全部收益。

## 7. 实验设计（可直接执行的判据）

### 7.1 实验臂（互相独立，不要混）

| 臂 | 修改时机 | 后缀 | 目的 |
|---|---|---|---|
| **K0** 基线 | 无 KV 操作 | — | 对照 |
| **K1** 轮末·等长替换 | 轮末 | 0 | **验证正确性**（收益小、风险最低） |
| **K2** 轮末·变长替换 | 轮末 | 0 | 验证 `seq_add` 补偿路径 |
| **K3** 中途·等长替换 | 中途 | >0 | **主要收益臂** |
| **K4** 中途·变长替换 | 中途 | >0 | 完整能力 |

**实施顺序：K0 → K1 → K2 → K3 → K4。** 不要跳步。

### 7.2 核心假设与证伪条件（写成 §6.6 那样的表）

| 假设 | 内容 | 证伪条件 |
|---|---|---|
| **KV-H1** | 手术后 L1 对账 100% 通过 | 任何一次 L1 不一致 → 实现有 bug，**不是**实验结论 |
| **KV-H2** | 等长替换的 L2 KV hash 与"全量重算"差异 < 容差 $\epsilon$ | 若远大于 $\epsilon$ → 手术改变了语义，需查 `seq_rm`/`decode` 顺序（缺陷 3） |
| **KV-H3** | 变长替换 + `seq_add` 后的输出质量不低于全量重算基线 | 若显著下降 → RoPE 补偿不完整 |
| **KV-H4** | 中途手术（K3/K4）的 `prefill_tokens_saved` > 0 且端到端更快 | 若墙钟未改善 → 手术开销吃掉收益，机制在**当前实现**下无实用价值 |
| **KV-H5** | 手术后的最终输出错误率 ≤ 全量重算 | 若更差 → 机制**有害**，必须报告为失败 |

**KV-H2 的容差 $\epsilon$ 必须在实验前标定**（用同配置连跑两次测自然漂移），
**不能事后按结果定**。这是防"先看结果再定标准"的关键。

### 7.3 必须同时跑的两条对照（防污染）

1. **同内容对照**：把"手术后的 KV"与"把完整最终文本重新 prefill 一遍的 KV"对比。
   **这是检验手术正确性的金标准**，比任何行为指标都可靠。
2. **空手术对照**：执行 `splice(i,i,[])`（空操作），确认结果**逐位不变**。
   若变，说明手术流程本身有副作用。

### 7.4 任务集选择

按 §6.2 的推论，**优先选长上下文 + 局部错误**的任务：

| 任务类型 | $L_p$ | 预期收益 |
|---|---|---|
| 长代码（>300 行，多文件） | 大 | ✅ 高 |
| 长文写作（>2000 字） | 大 | ✅ 高 |
| 短命令序列 | 小 | ❌ 趋近 0 |
| 混合 | 中 | 中 |

**短命令任务应作为"负对照"** —— 如果它也有大收益，说明测量有问题。

## 9. 常见错误清单（接手 Agent 逐条自查）

- ❌ 在**轮末**做手术却报告"省了半段输出"（后缀为 0，没有半段可省）
- ❌ 先 `decode` 新内容再 `seq_rm` 旧区间（缺陷 3，顺序反了）
- ❌ 客户端存字符串、下轮重新分词（缺陷 2）
- ❌ 用**闭区间**语义传给 `llama_kv_cache_seq_rm`（它是半开）
- ❌ 变长替换后**忘了** `seq_add` 补偿后缀位置
- ❌ 忘了 `llama_kv_cache_update()` → K-shift/defrag 未生效
- ❌ 把 L2 KV 字节相等当作判据（浮点 + 量化下不成立）
- ❌ 引入近似注意力（污染实验，禁止）
- ❌ 手术失败后**带着不一致的 KV 继续生成**（必须整轮作废）
- ❌ 只报省下的 token，不报手术开销与端到端墙钟
- ❌ 对短命令任务报告大收益（说明测量有问题）

## 12. 附录 A：关于"带着旧 KV 生成新 KV"的辨析（实测结论）

> 本节回应一个有理有据的反对意见："让模型带着旧 KV 生成替换内容，这样新 KV 里就同时留下了
> 『旧 KV 为什么错』和『新 KV 怎么修的』两种信息，省掉了错误摘要。"
>
> **结论：这个直觉有一半是对的，但整体不可用。实测差距约 70 万倍。**

### 12.1 先说对的那一半

反对意见里这个说法**是对的**：

> 新 token 的 K/V 是在**因果注意力**下、对包含旧 span 的整个上文算出来的，
> 因此**确实**隐含了旧内容的信息。

这不是空想。自注意力是加权求和，旧 span 作为上文被 attend 到，
其贡献会进入新 token 的隐藏状态，进而进入它的 K 和 V。**信息确实被保留了。**

### 12.2 再说致命的那一半

但这个"保留"是通过**污染**实现的，代价是**时间不一致**：

```
最终上下文（权威历史） = [A, B']          ← 旧 B 已被 B' 取代，不在历史里了
但 B' 的 KV 却是从 [A, B, B'] 算出来的    ← 它"记得"一个已经不存在的 B
```

**后果**：后续所有 token 的注意力都会**直接 attend 到"从未存在的历史"**。

这**不是近似误差，是把已删除的历史重新注入了注意力** —— 正是 v4.1 §4 定义的"下游扩散"，
也正是本机制存在的理由。用污染实现"记忆"，等于用病治病。

### 12.3 实测（可复现）

脚本：`experiments/verify_kv_replace_context.py`（纯 CPU，Qwen3-0.6B，几秒跑完）

方法：三份 KV 都与**金标准**比较 —— 即把**最终文本完整重新 prefill** 一遍得到的 KV。
谁更接近金标准，谁的 KV 就是时间一致的。

```
被修改 span 的 KV 与金标准的最大绝对差：
  路径 P（带旧 KV 算）    K: 118.658783     V:  62.019272
  路径 C（先删再算）      K:   0.000168     V:   0.000056
  前缀部分（两边都应完好）:   0.000000
```

| 判读 | 结论 |
|---|---|
| 路径 C ≈ 金标准（1.7e-4 = 正常浮点噪声） | 先删再算**等价于**完整重算 ✅ |
| 路径 P 偏离约 **70 万倍** | 带旧 KV 算**明显不等价于**完整重算 ❌ |
| 前缀差异 = 0 | 两种做法的前缀都未受损（符合预期） |

**这也顺带修正了本文档 §3 缺陷 1 里的一个说法**：
我曾写"**V 无位置编码 → V 永远可复用**"。这句话**只在"不改变上文"的前提下成立**。
实测 V 偏了 62 —— 因为 V 虽然不含位置编码，**但它是从"attend 过旧上文"的隐藏状态算出来的**。
准确表述应为：

> **K 受位置编码影响；V 不受位置编码影响，但 V 仍受"计算它时的上文"影响。**
> 所以"复用 V"也要求上文未变。

### 12.4 但反对意见里那半个真需求是合理且合法的

反对意见真正想要的是 **v0.2 §9.3 里明确列出的「erratum 追加」**：

> `v4.1` L39：**"修正只能追加"** —— 模型发现错了，只能在后续 token 里说"更正"。
> 但错误 token 仍留在上下文里，继续参与注意力计算。

也就是说：**"保留错误信息"是一个独立机制，它叫 erratum（勘误）追加**，
**不该由 KV 污染来实现**，而应通过**显式追加**实现：

```
正确做法：
  ① 模型带着旧 span 生成替换文本   ← 生成阶段能看到错误（生成替换文本必须能看到才知道怎么改）
  ② 丢弃①产生的 KV
  ③ 先 seq_rm 删旧 span
  ④ 在干净上下文里重新 decode 替换文本   ← 此时才产出最终 KV
  ⑤ 若要"勘误记录"，把它作为**显式文本**追加，并走 harness 审计日志
```

**关键区分（这一句要写进规范）**：

| 对象 | 是否应看到错误 | 理由 |
|---|---|---|
| **生成替换文本的过程** | ✅ 应该 | 不看到错误就不知道怎么改。这是"生成路径"问题 |
| **替换文本最终的 KV** | ❌ 不应 | 必须与"从未出错"的历史一致。这是"状态一致性"问题 |

**两者不矛盾**：模型在生成时看到了错误 → 所以**它写出的正确文本本身就已经体现了修正**
（比如从 `reslt` 变成 `resul`）。这个信息**在文本里**，不需要再往 KV 里塞。

### 12.5 一个必须澄清的原始动机错误

原始描述里说"保留为什么错的信息"是因为：

> "替换部分实际上是有受到曾经坏 token 和坏 KV 导致的后续字段隐形 KV 向量影响积累的影响的"

这里混了两件不同的事：

| | 是什么 | 该不该保留 |
|---|---|---|
| **坏 token 的内容** | 模型本来就知道"我刚才写了 X"（在上下文里） | 生成时需要；KV 里不该留 |
| **错误造成的下游 KV 偏移** | 坏 KV 对后续 token 的**污染** | **必须清除**（v4.1 §4 的核心要求） |

原描述把"污染"当成了"信息"。**污染是病，不是记忆。**

### 12.6 无成本的替代方案（推荐）

如果要"错误信息"，有一个**零成本且更可靠**的做法：**用已有的审计日志**。

```
harness/core/audit_logger.py   ← 已存在，JSONL 不可变
```

模型的 KV 修改工具调用本身就带 `target_text` / `op` / `reason`
（见 `harness/core/tool_call_parser.py` 的 `_DRAFT_COMMIT_REVISION_SCHEMA`）。
把这些写进审计日志，就得到了**完整、可查、可复现**的"为什么错"记录，
而且：

- 不污染 KV ✅
- 不占 KV 预算 ✅
- 可统计（§11.2 的"修订栈主动触发分布"正需要它）✅
- 符合铁律 9「审计不可变」✅

**结论：要错误信息就写审计日志，不要往 KV 里塞。**

### 12.7 本节的最终裁定

| 主张 | 裁定 |
|---|---|
| "新 KV 隐含了旧内容信息" | ✅ **成立**（注意力机制决定的） |
| "因此应该带着旧 KV 算" | ❌ **不成立**（实测偏离金标准 ~70 万倍，破坏时间一致性） |
| "要保留为什么错的信息" | ✅ **需求合法**，但应由 **erratum 显式追加 + 审计日志** 实现 |
| "V 无位置编码所以永远可复用" | ⚠️ **需修正**：V 不含位置编码，但仍受计算时的上文影响 |

**若仍要验证"带旧 KV 算"的实际影响**：把它作为一个**独立实验臂 K5**，
用 §7.3 的"同内容对照（与完整重新 prefill 比 KV）"来测。
**可以试，但不能作为主路径**，且必须如实报告它破坏了时间一致性。

## 13. 附录 B：delete / insert 是否也存在同样的 KV 破坏？（实测结论）

> 本节回应："删除和插入这两种操作是否也存在 KV 破坏重算的问题？被删除的 KV 通常是多写了，
> 但他们的影响仍然继承到了后续 KV 中。"

**结论：是，两者都存在，而且与 replace 不等长是「同一个」破坏机制，不是新问题。**
**但 delete 与 insert 之间有一条关键不对称，它决定了哪一种值得做。**

### 13.1 破坏机制是同一个

三种操作对 KV 的影响可以完全归一：

| 操作 | 长度变化 | 后缀位置 | 后缀 KV |
|---|---|---|---|
| `replace`（等长） | $\Delta = 0$ | 不变 | **可复用** |
| `replace`（变长） | $\Delta \ne 0$ | 平移 | **失效，需重算** |
| `delete` | $\Delta = -(j-i) < 0$ | 左移 | **失效，需重算** |
| `insert` | $\Delta = +m > 0$ | 右移 | **失效，需重算** |

**本质只有一条**：$|\Delta| \ne 0$ → 后缀位置整体偏移 → 后缀 K 的 RoPE 失效 → 必须重编码。
`delete`/`insert` 相对 `replace` **没有引入新的破坏类型**，它们只是 $\Delta \ne 0$ 的两种具体形态。

所以 §4.3 的执行序列对三者**完全一致**，`seq_add(start+new_len, -1, delta)` 一条补偿路径通吃。

### 13.2 但"删除会破坏后缀"这个直觉，比"插入会破坏"要弱

原始提问的直觉是："被删除的内容多半是**多写了**，所以后缀文本应该还站得住"。

**这个直觉在文本层面常常成立，但在 KV 层面不成立** —— 两者要分开看：

| 层面 | delete | insert |
|---|---|---|
| **后缀 KV** | ❌ 必须重算（位置变了） | ❌ 必须重算（位置变了 + 新内容该被注意到） |
| **后缀文本** | ⚠️ **可能仍然有效**（删的是冗余内容） | ❌ **几乎必然失效**（新内容会改变后续该怎么写） |

**为什么 delete 的后缀文本可能仍有效**：如果被删的是一段冗余（重复行、多余日志、临时调试语句），
那么"没有它"的历史下，后续文本往往**本来就是那样写的**。

**为什么 insert 几乎必然无效**：插入的内容**改变了后续应该写什么**。
例如插入一个新参数后，后面的调用点、类型标注、文档字符串**都该跟着变**。
因此插入若要正确，**后缀文本也得重生成** —— 那就等于**从插入点整段重写**，
**KV 手术的收益直接归零**（回到 §6.1 的全量重算）。

### 13.3 实测（可复现）

脚本：`experiments/verify_delete_insert_damage.py`（纯 CPU，几秒）

```
token 数: head=3  body(待删/插入)=11  tail=5

D1  删除中间 span，重算后缀 KV  vs  短文本完整 prefill
      K 最大绝对差 = 0.000168
      V 最大绝对差 = 0.000053
      前缀(head)差异 = 0.000084

I1  中间插入 span，重算后缀 KV  vs  完整 prefill（同一序列）
      K 最大绝对差 = 0.000137
      V 最大绝对差 = 0.000072

C0  空操作 splice(i,i,[])  vs  同输入再算一次   <- 噪声底
      K 最大绝对差 = 0.000000000
      V 最大绝对差 = 0.000000000
```

**判读**：

| 观察 | 结论 |
|---|---|
| C0 = **精确 0** | diff 函数可信；同时证明**同输入下 KV 是确定性的**（可复现） |
| D1 / I1 ≈ **1.4e-4** | 比噪声底高约 3 个数量级，但**远低于**路径 P 的 118 |
| 与附录 A 路径 C 的 **1.7e-4 同量级** | **三者一致**：delete / insert / 等长替换的"先删再算"都等价于完整重算 ✅ |

**所以 §4.3 的执行序列对 delete 与 insert 同样成立，不需要额外机制。**

### 13.4 一个必须区分的判据：「KV 重算」≠「文本重生成」

这是本节最重要的产出。**两件事必须分开决策**：

| 决策 | 判据 | 谁来做 |
|---|---|---|
| **后缀 KV 要不要重算** | 永远要（只要 $\Delta \ne 0$） | 服务端，**无选择余地** |
| **后缀文本要不要重生成** | 看"后缀文本在修改后的历史下是否仍然自洽" | harness / 模型，**有选择余地** |

**可测量的判据（写进实验设计）**：

```
对后缀的每个 token t_k（k 在后缀内）：
    比较  P(t_k | 修改后的历史)  与  P(t_k | 修改前的历史)

  - 若两者接近        -> 后缀文本仍自洽，可保留（delete 常见）
  - 若显著下降        -> 后缀文本不自洽，必须重生成（insert 常见）
```

**这个判据必须实测，不能靠直觉。** 本节的例子（工程性代码）中，
delete 后后缀的下一个 token top-1 仍然相同，但 **top-5 已经明显不同**
（`['print','f','其中',...]` vs `['print','输出','运行',...]`）——
**"top-1 相同"是弱证据，不足以断言语义完好。**

### 13.5 对实施顺序的影响（重要）

| 操作 | 中途使用 | 轮末使用 |
|---|---|---|
| `replace` 等长 | ✅ 主收益臂（K3） | ✅ 验证正确性（K1） |
| `delete` | ⚠️ 取决于 §13.4 判据；后缀文本可能仍有效 → **值得单独测** | ✅ 可行 |
| `insert` | ❌ **收益归零**（后缀文本多半要重生成 = 整段重写） | ✅ **唯一合理用法** |

**结论**：
- **`insert` 只做轮末**（追加缺失行/参数），中途插入不要做——那不是省算力，是自欺。
- **`delete` 值得作为独立实验臂**，因为"删冗余"是真实场景，且后缀文本可能真的不用重生成。
- 建议新增实验臂：**K6 = 中途 delete**，并配 §13.4 的判据测量"后缀文本自洽率"。

### 13.6 修正 §3 缺陷 1 的表述

原文把问题归为"不等长替换"，**范围说窄了**。准确表述应为：

> **任何 $|\Delta| \ne 0$ 的编辑**（变长替换 / 删除 / 插入）都会使后缀位置偏移，
> 从而使后缀 K 的 RoPE 失效，必须用 `seq_add` 补偿重编码。

## 14. 附录 C：为什么"注意力抹除/追加"贵，以及稀疏注意力为什么可能改变结论

> 起因：一个判断 —— "注意力抹除与注意力追加在当前架构下做不到，除非接受大量重算；
> 只有 KV 替换能做"。**这个判断一半对、一半过早放弃**。本节给出成本分层、
> 说明贵在哪、以及稀疏注意力为什么可能把结论翻转。

### 14.1 先纠正：成本不是二分的，是三层

原判断把成本看成"复用 vs 大量重算"两极。实际有三层，**中间那层被漏掉了**：

| 层 | 操作 | 代价 | 是否可用 |
|---|---|---|---|
| **L-a 位置平移** | `seq_add` 对后缀 **K** 重做 RoPE | **低** | ✅ 本地已有（`llama.h` L920） |
| **L-b 表示重算** | 重算后缀的**隐藏状态** → 重算 K/V | **中** | ⚠️ 可做，但代价 = 一次重算后缀 |
| **L-c 文本重生成** | 让模型重新"写"后缀 | **高** | ❌ 等于整段重写，收益归零 |

**关键事实**：
- `seq_add` 只重做 **K**（RoPE 作用在 K 上）。**V 无位置编码，不需要重做** —— 这是免费的。
- 所以"位置偏移"本身**非常便宜**，不是"大量重算"。
- 真正贵的是 **L-b**：要让后缀的 K/V 反映"新历史下的注意力"，就得重算后缀的**隐藏状态**。
  **这已不是"改 KV"，而是"重算一层表示"。**

**所以准确表述是**：

> 位置平移便宜（L-a）；**注意力改变贵（L-b）**；文本重生成最贵（L-c）。
> 原判断说的"贵"是 L-b，不是 L-a。

### 14.2 为什么"抹除"和"追加"都落在 L-b

**抹除（delete）为什么不是删掉 KV 就完事**：

K/V 是**张量**，可以删。但"坏 token 的影响"不只在它自己的 K/V 里，
而是**已经烘进了下游 token 的隐藏状态**（进而进了它们的 K/V）。
删掉坏 token 的 K/V，只是让它**不再被 attend 到**；
下游 K/V 里那份"被污染过的表示"**仍然在**。

要做到真正的"抹除"，必须让下游 token 的隐藏状态**在"没有那个 token"的历史下重新算一遍**
→ 这就是 **L-b**。

**追加（insert）为什么更贵**：

新 span 插入后，每个后缀 token **本应 attend 到它**，但它们的历史里没有它。
它们的表示"缺了一次注意力"。
要补上，同样要重算后缀隐藏状态 → **L-b**；
**而且**后缀文本本身可能也得改写 → 再叠 **L-c**。

**结论**：erase 与 append 的代价同源于"**改变了下游的注意力模式**"，
与"KV 长度变没变"**不是**同一件事。长度变化只带来便宜的 L-a。

### 14.3 但有一件事原判断说对了：**在稠密注意力下，L-b 的代价是"整条后缀"**

稠密注意力（dense attention）的定义就是：**每个 query attend 到所有历史**。
因此改动**任意一处**历史 → **变更传播到每一个后缀 token** → L-b 的代价 = 整个后缀。

**这就是"大量重算成本"的真正来源** —— 不是 KV 拼接，而是**稠密注意力让影响范围无界**。

**关键推论（本附录的核心）**：

> **影响范围是由注意力模式决定的，不是由编辑操作决定的。**
> 稠密注意力 → 影响范围 = 整条后缀 → 局部重算无意义。
> **稀疏注意力 → 影响范围有界 → 局部重算变得可行。**

### 14.4 稀疏注意力为什么可能翻转结论

稀疏注意力的定义是：**每个 query 只 attend 到 top-k 个选中的历史位置**，不是全部。

这对 KV 手术的意义是**结构性的**：

| | 稠密注意力 | 稀疏注意力 |
|---|---|---|
| 一个历史位置被多少 query attend | **全部** | **少数** |
| 删/插一个 span 的影响范围 | 整条后缀 | **仅"选过它的那些 query"** |
| L-b 重算代价 | $O(\text{后缀长度})$ | $O(\text{受影响 query 数})$ |
| 局部重算的价值 | 无 | **有** |

**换句话说**：稀疏注意力**把"编辑的影响半径"从无界变成有界**。
在有界影响半径下，"只重算受影响的那一小撮"**才第一次成为有意义的工程**。

这就是为什么该方向值得研究，而**不是**因为它"更快"。

### 14.6 一个稀疏注意力给 KV 手术带来的**新问题**（这是研究空白点）

稀疏注意力**不是**只在帮忙，它**引入了一个稠密注意力下不存在的问题**：

```
稀疏注意力需要为每个 query 维护"选中的 KV 位置集合"（检索索引）。
一旦 KV 被编辑（删除/插入/替换）：
  - 被删位置的索引 -> 变成悬空引用
  - 位置平移后      -> 索引需要整体重映射
  - 新插入的位置    -> 从未被任何 query 选过（它没参与过任何检索）
```

**所以"稀疏注意力 + KV 编辑"需要一套新的索引维护机制**，
而这个机制在现有文献里**没人做**（至少在本次检索范围内没看到）。

**这就是可发表的研究空白，而且它是被你的实验问题自然逼出来的。**

### 14.7 建议的研究方向（按可执行性排序）

| 优先级 | 方向 | 为什么可行 |
|---|---|---|
| **R1** | **稀疏注意力下 KV 编辑的影响半径测量** | 先**测量**不先发明：给定一次编辑，实际有多少 query 选了受影响的位置？这个数字决定了后续一切 |
| **R2** | **有界重算（bounded recompute）** | 只重算"选过受影响位置"的 query 及其下游。稀疏性使其有界 |
| **R3** | **稀疏索引的编辑一致性维护** | §14.6 的空白点。删/插/移后如何维护检索索引 |
| **R4** | **近似补偿的误差界** | 不做精确重算，而做"有误差保证的补偿"。⚠️ 需要误差上界，否则污染实验（对比 §3 缺陷 8） |
| **R5** | **erratum 显式追加 + KV 手术的组合** | v0.2 §9.3 的 erratum 与本机制组合，可能比二者单独都强 |

**R1 必须最先做**：它是**测量**，不是发明，成本最低、信息量最大，
而且**它的结果直接决定 R2–R4 值不值得做**。

### 14.8 对当前阶段（纯提示词验证）的影响

**没有影响，也不该有影响。** 理由：

1. 稀疏注意力**需要训练时原生引入**（NSA 强调"natively trainable"）。
   **不能在现成模型上后加** —— 后加等于改变了模型行为，会污染实验。
2. 因此稀疏注意力属于**下一阶段**的技术底座，**不能用来回答"提示词能带来多少收益"**。
3. 当前阶段（v0.2 §6.2 的 A–H + 提示词强度）**继续按原计划走**，不受本附录影响。

**本附录的产出是一个"方向"，不是一个"改动"。** 它应该写进新规范的"后续路线图"章节，
而不是塞进当前实验。

### 14.9 本附录的最终裁定

| 判断 | 裁定 |
|---|---|
| "注意力抹除/追加做不到，除非大量重算" | ⚠️ **在稠密注意力下成立**；原因是影响范围无界，不是 KV 不可改 |
| "只有 KV 替换能做" | ❌ **过早放弃**。替换（等长）只是因为 $\Delta=0$ 而**无需重算**，不是因为它在原理上更优越 |
| "下一个方向是：局部注意力被打破后如何低成本更新受影响的 KV" | ✅ **准确，而且这正是本文档该输出的东西** |
| "稀疏注意力有没有借鉴空间" | ✅ **有，而且是结构性的**：它把影响半径从无界变有界（§14.4） |
| "这是本次探索在学术上最有价值的产出" | ✅ **同意**。机制本身的工程价值有限，**它逼出的问题定义才是产出** |
