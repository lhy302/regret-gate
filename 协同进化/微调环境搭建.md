## 3. 显存现实与可行路径

### 3.1 为什么 4 GB 很紧

训练显存 ≈ **权重 + 梯度 + 优化器状态 + 激活**。

| 配置 | 粗算显存 | 4 GB 可行性 |
|---|---|---|
| 0.6B 全参 bf16 + Adam | 1.2 + 1.2 + 4.8 + 激活 ≈ **7.2 GB+** | ❌ |
| 0.6B LoRA（bf16 基座） | 1.2 + 少量 LoRA 状态 + 激活 ≈ **2–3 GB** | ⚠️ 短序列勉强 |
| **0.6B QLoRA（4bit 基座）** | 0.4 + LoRA 状态 + 激活 ≈ **1–1.5 GB** | ✅ **推荐起点** |
| 4B 全参 | ≈ **48 GB+** | ❌ |
| 4B QLoRA（4bit） | 2.4 + 状态 + 激活 ≈ **4–6 GB** | ⚠️ 需极限省显存 |
| 4B LoRA（bf16） | 8 + … | ❌ |

### 3.2 省显存的必备开关

```yaml
# ms-swift / LLaMA-Factory 通用思路
load_in_4bit: true              # QLoRA 量化基座
gradient_checkpointing: true    # 用时间换显存，必开
per_device_train_batch_size: 1
gradient_accumulation_steps: 8  # 用累积代替大 batch
max_length: 1024                # ⚠️ 从短序列起步
lora_rank: 8                    # 先小后大
optim: paged_adamw_8bit         # 优化器状态分页
bf16: false                     # ⚠️ Pascal 6.1 对 bf16 支持差，用 fp16
fp16: true
```

⚠️ **Pascal（6.1）注意**：原生 bf16 支持不完整，**用 fp16 更稳**。但 fp16 训练需要 loss scaling（`transformers`/`trl` 默认会处理）。

### 3.3 与规范 §11 的矛盾（重要）

`v0.2 §11.1` 要训练的五项能力：

- A 生成中主动回头检查
- B 错误发现与归因
- C 写手 + 审稿人双能力
- D 修订质量与最小改动
- E 尾部自审的服从性与有效性

**这五项都是"长序列上的行为塑造"** —— 而长序列 + 大 batch 正是 4 GB 显存最承受不住的组合。缩到 1024 长度做出来的行为，**未必迁移到目标场景的长对话**。这一点必须写进新规范的成功判据里（见 `规范缺口与阶段定位.md` §3.3）。

### 3.4 三条路径对比

| 路径 | 成本 | 能做到什么 | 建议 |
|---|---|---|---|
| **本机 0.6B QLoRA** | ￥0 | 打通全链路；短序列行为验证 | ✅ **先做这个**，把流程跑通 |
| **租云 GPU**（单卡 24 GB） | 按小时 | 0.6B/4B LoRA 甚至 4B 全参；长序列 | ✅ **真正的对照实验在这里做** |
| 本机 CPU 训练 | ￥0 | 技术上可行，慢到不实用 | ❌ 不建议 |

## 4. Qwen3-4B 对照模型获取

你的对照实验需要**同族**的 4B。国内可达渠道：

### 方式 A：hf-mirror（推荐，官方原版）

```powershell
$env:HF_ENDPOINT = "https://hf-mirror.com"
$py = "D:\工作区表\工作区4\协同进化\.venv-finetune\Scripts\python.exe"
& $py -c "from huggingface_hub import snapshot_download; snapshot_download('Qwen/Qwen3-4B', local_dir=r'D:\工作区表\工作区4\协同进化\models\Qwen3-4B')"
```

### 方式 B：ModelScope（阿里官方镜像，通常最快）

```powershell
& $py -m pip install modelscope
& $py -c "from modelscope import snapshot_download; snapshot_download('Qwen/Qwen3-4B', local_dir=r'D:\工作区表\工作区4\协同进化\models\Qwen3-4B')"
```

### 方式 C：git + LFS

```powershell
git lfs install
git clone https://hf-mirror.com/Qwen/Qwen3-4B "D:\工作区表\工作区4\协同进化\models\Qwen3-4B"
```

**体积**：Qwen3-4B bf16 约 **8 GB**。D 盘剩余 1.7 TB，空间充足。

> **我没有替你下载**：因为本机 4 GB 显存在 4B 上只能勉强 QLoRA，如果你打算走云 GPU，本地留一份 8 GB 权重可能没必要。**你说下就下**（约 8 GB，视网速 10–40 分钟）。

### 对照实验要用哪个变体？

Qwen3 有 **Base** 和 **Instruct**（以及 Thinking 变体）之分：

- **`Qwen/Qwen3-4B`** = Base（预训练基座）
- **`Qwen/Qwen3-4B-Instruct-2507`** 等 = 指令微调版

**你的 0.6B 是 `Qwen/Qwen3-0.6B`（Base）**，所以对照实验**应当也用 Base（`Qwen/Qwen3-4B`）** —— 否则"同族同后训练收益对照"里混入了 Instruct 微调这个额外变量，结论会被污染。

## 5. 打通链路的推荐流程

先用**官方现成配置**改一版，不要从零写训练脚本。

### 5.1 参考文件（已下载）

```
finetune/Qwen3/examples/llama-factory/qwen2-7b-qlora-sft.yaml   ← 改成 Qwen3-0.6B
finetune/Qwen3/docs/source/training/ms_swift.md                 ← ms-swift 官方步骤
finetune/Qwen3/docs/source/training/unsloth.md                  ← 省显存方案
finetune/Qwen3/docs/locales/zh_CN/LC_MESSAGES/training/*.po     ← 中文版
```

### 5.2 三选一

| 框架 | 优势 | 适合 |
|---|---|---|
| **ms-swift** | 与 Qwen 同厂，Qwen3 支持最及时 | ✅ 首选 |
| Unsloth | 最省显存 | 4 GB 场景优先评估 |
| LLaMA-Factory | 生态最大、有 WebUI | 想要图形界面时 |

### 5.3 闭环验证（必须走完一遍再谈实验）

```
① 准备一个 20–50 条的小数据集（先别管质量，只为验证链路）
        ↓
② QLoRA SFT 跑通（能出 checkpoint）
        ↓
③ 合并 LoRA 到基座（merge）
        ↓
④ 转 GGUF（可用已有的 convert_hf_to_gguf.py）
        ↓
⑤ 用 llama-server 加载微调后的模型，发一个真实请求
        ↓
⑥ 对比微调前后同一 prompt 的输出
```

**只有第 ⑥ 步有差异，才说明链路真的通了。** 前面五步全绿但第 ⑥ 步无差异，说明数据/超参没起作用，不是"环境搭好了"。

### 5.4 数据格式

按 `v0.2 §11.1` 每项能力给出的"训练数据形态"设计：

| 能力 | 数据形态（原文） |
|---|---|
| A 主动回头检查 | 正向：调用 `draft.commit_revision` 并成功修正的轨迹；负向：有明显错误未自检的轨迹；偏好对：自检 vs 不自检 |
| B 错误发现与归因 | 三元组 `(原始输出, 错误位置与原因, 修订后输出)`；审查对 `(他人代码, 结构化错误清单)`；归因标注 |
| C 双能力并存 | 混合批次（生成+审查+修订）；输入显式标记角色（写手/审稿人/修订者） |
| D 最小改动 | 偏好对 `(大范围重写, 最小修订)`，用于 DPO；修订轨迹用于奖励建模 |
| E 尾部自审服从性 | 正向：尾部自审中发现并修正；负向：形式化自审；偏好对：认真 vs 敷衍 |

**注意**：A、D、E 明确要**偏好对（preference pairs）** → 这意味着不只是 SFT，还要 **DPO**。`trl` 里 `SFTTrainer` 和 `DPOTrainer` 都有，环境已装。
