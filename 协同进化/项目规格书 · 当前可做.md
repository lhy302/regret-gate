# P1 · 提示词潜力验证（真实模型）

## 目标

在**模型权重不变**的前提下，测量"提示词提醒回头检查"与"AI 偶发发现问题回头修改"能带来多少收益。

## 为什么现在能做

- harness 已完整实现且 **268 tests 全绿**
- A–H 组 + H 三档提示词强度（none/weak/strong）**配置与代码都已就绪**
- 只需把后端从 `FakeClient` 换成**真实模型**

## ⚠️ 关键前提：离线结果不能回答这个问题

实测证据（`harness/runs/report.md` L37–39）：

```
H-none   语法错误率 0.2500  逻辑错误率 0.2500  任务成功率 0.5000
H-weak   语法错误率 0.2500  逻辑错误率 0.2500  任务成功率 0.5000
H-strong 语法错误率 0.2500  逻辑错误率 0.2500  任务成功率 0.5000
```

**三档完全相同** —— 因为 `FakeClient` 不读提示词。
→ 离线跑通只证明**链路与指标口径**正确，**证明不了提示词有任何作用**。
**P1 的全部价值就在于用真实模型把这三档拉开。**

## 具体任务

### 1.1 选定真实后端
两条路，建议**先本地、后托管**：

| 路线 | 后端 | 优点 | 缺点 |
|---|---|---|---|
| **A. 本地** | 已有 `llama-server.exe` + Qwen3 模型 | 免费、无速率限制、可复现（固定 seed） | 需 `D:\my-project\ai-server` 目录可访问（检查 360 白名单） |
| **B. 托管** | OpenAI / Anthropic（环境变量 `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`） | 模型能力强，结论更可信 | 需密钥、有成本、需固定模型版本 |

**建议 A 起步**：先在本地把链路跑通（快、免费），再用 B 得到可对外的结论。

### 1.2 固定可复现性（铁律 10）
- 模型版本**写死**（如 `gpt-4o-2024-08-06` 或本地 gguf 的 SHA）
- 固定 `temperature` / `top_p` / `seed`
- **记录到 `harness/runs/run_meta.json`**

### 1.3 跑最小可行集
```powershell
cd harness
# 先单组小规模确认链路
py -3.12 -m experiments.runner --group H --limit 5
# 再放量
py -3.12 -m experiments.runner --group H --limit 20
```

### 1.4 关键：必须产出"三档拉开"的证据
| 观察 | 含义 |
|---|---|
| H-none ≈ H-weak ≈ H-strong | ⚠️ 与离线同结果 → **说明后端没接上真实模型**，不是"提示词无效" |
| H-strong 显著优于 H-none | 提示词有效，测出**能力上限** |
| H-none 接近 0 且 H-strong 高 | 有能力但需强信号 → **后训练可能有价值**（v0.2 §1.4） |

### 1.5 按 v0.2 §1.4 的解读矩阵下结论
| A | B | C | 解读 |
|---|---|---|---|
| ≈0 | 高 | 中 | 有能力，需强外部信号。后训练可能有价值 |
| ≈0 | 低 | ≈0 | 缺乏底层能力。后训练大概率无效 |
| ≈0 | 高 | ≈0 | 只在明确命令下才动。后训练需解决"无命令时也动" |
| 中 | 高 | 中 | 已有自发倾向。harness 机制可直接受益 |

## 交付物

- `harness/runs/`（真实模型的分析结果）
- `harness/report.md` 更新版（**必须标明数据来自真实模型，而非 FakeClient**）
- 一份结论：落在 v0.2 §1.4 矩阵的哪一格

## 验收判据

| 判据 | 通过条件 |
|---|---|
| A1 | **H 三档不再完全相同**（若相同，先查后端是否生效，不要下结论） |
| A2 | 每组 ≥ 20 次运行，且 `failures == 0` |
| A3 | 报告含**分布**（不只均值）与**置信区间**（v0.2 §6.5） |
| A4 | 明确声明数据来源与适用范围（真实 API / 本地模型 / 模型版本） |
| **A5** | **若三档无差异，如实报告"未观察到提示词效应"，并注明是否已达到最小可检测效应** |

## 风险与陷阱

| 风险 | 应对 |
|---|---|
| 后端没接上，误得"提示词无效" | 先看 `run_meta.json` 的 `provider` 字段；或故意用强提示跑一条看输出变化 |
| 本地模型太弱，测不出上限 | 记录模型名；必要时用托管模型复测 |
| `D:\my-project\ai-server` 被拦 | 见 `README.md` §6 的环境注意事项 |
| 长代码任务生成慢 | 先 `--limit 5` 验证，再放量 |

## 依赖

无。**本项目与其它项目完全并行。**

## 预估

1–2 天（含后端调试与放量跑）。

# P2 · KV 编辑正确性验证套件

## 目标

把散落在 `experiments/` 的四个一次性脚本，整合成**可重复运行的验证套件**，作为 G2 与 P5 的**测量工具**。

## 为什么现在能做

- 本地 `ik_llama.cpp` 的 `llama_kv_cache_seq_rm` / `seq_add` / `update` **全部存在**（`include/llama.h` L898/926/966）
- 已有 2 个脚本与 **4 项实测结论**（含噪声底）
- 纯 CPU 即可跑，不需要 GPU

## 具体任务

### 2.1 整合现有脚本
| 现有脚本 | 整合为 |
|---|---|
| `experiments/verify_kv_replace_context.py` | `suite/test_01_replace_context.py` |
| `experiments/verify_delete_insert_damage.py` | `suite/test_02_delete_insert.py` |

### 2.2 补齐三个未验证项
| 编号 | 待验证 | 为什么重要 |
|---|---|---|
| **T3** | **不等长替换 + `seq_add` 位置补偿**是否真能恢复一致 | 缺陷 1 的修正**尚未验证**——目前只验证了"先删再算"，没验证"补偿后缀" |
| **T4** | **"只重算 K、V 直接拷贝"** 是否可行 | 我在附录 A 承认过一处错误（"V 永远可复用"），**需量化影响面** |
| **T5** | **空手术 `splice(i,i,[])` 逐位不变** | `INV-8` 原子性；已有噪声底为 0 可对照 |

### 2.3 定义容差 ε
- 用**同输入连跑两次**的差异作噪声底（实测为 **精确 0**）
- 据此把 ε 定在噪声底之上、远离错误量级的位置
- ⚠️ **ε 必须在实验前标定，不能事后按结果定**

### 2.4 输出结构化结果
- 每次运行输出 JSON（含 `case` / `K差` / `V差` / `噪声底` / `判定`）
- 便于 P5 与 G2 直接复用

## 验收判据

| 判据 | 通过条件 |
|---|---|
| B1 | T1/T2 复现既有结论（路径 C ≈ 噪声底；路径 P 差 5 个数量级以上） |
| B2 | **T3 给出明确结论**：`seq_add` 补偿后与完整重算的差异 < ε 或 ≥ ε |
| B3 | **T4 给出明确数字**：只重算 K、拷贝 V 的偏差量级 |
| B4 | T5 空手术差异 == 0（或明确报告非 0 及其量级） |

无。**但它的产出是 G2 与 P5 的输入。**

1–2 天。

# P3 · 微调闭环打通（Qwen3-0.6B QLoRA）

## 目标

跑通 `数据 → QLoRA SFT → merge → GGUF → 推理` 全链路，**并证明微调前后有可观察差异**。

## 为什么现在能做

- 权重已核验（原始 bf16，未被改动）
- 官方微调文档与示例 yaml 已下载（`finetune/Qwen3/`）
- `setup_微调环境.ps1` 已写好（含 **UTF-8 BOM**，语法已校验）

## ⚠️ 硬约束

| 约束 | 后果 |
|---|---|
| **显存 4 GB** | 只能 **QLoRA + gradient_checkpointing + 短序列** |
| compute 6.1 (Pascal) | **用 fp16 不用 bf16** |
| 0.6B 全参 SFT 需 ~7.2 GB | ❌ 不可行 |

## 具体任务

### 3.1 建环境
```powershell
powershell -ExecutionPolicy Bypass -File "D:\工作区表\工作区4\协同进化\setup_微调环境.ps1"
```
**出口判据**：输出 `cuda 可用 = True`。若为 False，说明装成了 CPU 版，重装 cu121。

### 3.2 造一个 20–50 条的小数据集
- 只为**验证链路**，不追求质量
- 按 v0.2 §11.1 的"训练数据形态"设计（先挑**最容易做的一种**，例如**能力 E：尾部自审服从性**的正/负样本）

### 3.3 用官方 yaml 改一版
参考 `finetune/Qwen3/examples/llama-factory/qwen2-7b-qlora-sft.yaml`，改关键项：
```yaml
load_in_4bit: true
gradient_checkpointing: true
per_device_train_batch_size: 1
gradient_accumulation_steps: 8
max_length: 1024          # 从短序列起步
lora_rank: 8
fp16: true                # Pascal 不用 bf16
```

### 3.4 走完六步闭环
```
① 小数据集  →  ② QLoRA SFT 出 checkpoint  →  ③ merge LoRA
     →  ④ 转 GGUF（用已有 convert_hf_to_gguf.py）
     →  ⑤ llama-server 加载  →  ⑥ 同一 prompt 对比微调前后输出
```

### 3.5 ★ 第 ⑥ 步是唯一有效的验证
**前五步全绿但第 ⑥ 步无差异 = 链路没起作用，不是"环境搭好了"。**

## 交付物

- `协同进化/finetune/runs/<日期>/`（配置、日志、checkpoint）
- 微调后的 GGUF
- 微调前后同一 prompt 的输出对比记录

## 验收判据

| 判据 | 通过条件 |
|---|---|
| C1 | `torch.cuda.is_available() == True` |
| C2 | SFT 跑完并产出 checkpoint（无 OOM） |
| C3 | merge + 转 GGUF 成功，GGUF 头可解析（复用 `gguf_check.py` 思路） |
| C4 | `llama-server` 能加载并返回结果 |
| **C5** | **同一 prompt 下，微调前后输出存在可观察差异** |
| **C6** | **若 C5 无差异，如实报告"链路跑通但训练未产生可观察影响"，并排查数据/超参** |

## 风险与陷阱

| 风险 | 应对 |
|---|---|
| OOM | 降 `max_length` → 降 `lora_rank` → 开 `paged_adamw_8bit` |
| `bitsandbytes` 在 Windows 上装不上 | 退化为**非量化 LoRA**（0.6B 的 bf16 基座约 1.2 GB，勉强可试） |
| 数据集太小导致无差异 | 这是**预期的**；本项目的目的是**打通链路**，不是出效果 |
| 把"跑通"当成"有效" | **C5/C6 是硬判据** |

## 依赖

无（可与 P1/P2 并行）。

## 预估

2–3 天（含环境与排障）。
