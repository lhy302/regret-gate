## 二、三个 🔴 级错误

### 🔴 1. 你假定"修改点之后全部复用"——不等长时这是错的

你的例子：

```
替换段 01010101010 (11位)  →  111111111111 (12位)   ← 不等长
最终结果 [1010111111111111010101010101010]
```

一旦长度变了，**其后所有 token 的位置整体平移**，而 **K 里已经烘焙了 RoPE**。

关键数学事实（多篇文献共用）：

$$\mathrm{PE}_i(m)^\top \mathrm{PE}_i(n) = \cos\big((m-n)\theta_i\big)$$

**RoPE 只依赖相对位置差**。所以：

| | 等长替换 | 不等长替换 |
|---|---|---|
| 后缀相对位置 | 不变 | **全变** |
| 后缀 **V** | 可复用 | **可复用**（V 无位置编码） |
| 后缀 **K** | 可复用 | **必须重编码** |

你漏的是最后一行。修正只需加一步 `seq_add(新段末, -1, delta)`——但**漏了后缀就是错的**。

### 🔴 2. 客户端存字符串、下轮重新分词 → 对账必然失败

BPE 分词**不可逆**。你拼出的字符串下轮重新分词，边界会跑到不同位置：

```
原生成 token:  ["def"," foo","(x)",":"]   → 4 个
改后字符串:    "def bar(x):"
重新分词:      ["def"," bar","(x):"]      → 3 个   ← 对不上
```

服务器 KV 是 4 槽，客户端说 3 个 → **前缀头对不上，整个机制崩掉**。

**这条最危险，因为它不可调试**——表现为"偶尔对得上、偶尔对不上"。

**修正**：权威存储必须是 **token id 序列**（不是字符串），下轮用扩展协议显式传 token id，**别让服务端重新分词**。

### 🔴 3. 你没定义"先删旧 KV、再算新内容"的顺序

新内容如果是**带着旧 KV** 生成的，它的 K/V 就承载了本应被删掉的信息——这正是 v4.1 说的"时间混乱"。

**正确顺序（③ 必须在 ④ 之前）**：
```
③ llama_kv_cache_seq_rm(span_start, span_end)   ← 先删，彻底去掉坏内容

## 三、还有 7 个问题（🟠🟡）

- **🟠 你自己的例子算术不自洽**：被替换 11 位、新内容 12 位，但最终结果按 29 位写的（前缀3+12+后缀15=30）。**长度语义没定义** → 建议 v1 **只做等长替换**。
- **🟠 对账不能要求逐位相等**：你生产配置用了 `-ctk q4_0 -ctv q4_0`，**KV 本身是有损的**；浮点加法顺序、后端差异也会导致按位不同。应分两层：**L1（token id + 位置）严格相等** = 真契约；**L2（KV 字节）只作诊断**。
- **🟠「保留了为什么错的信息」这个假设不成立**：按修正后的流程，替换内容是在**删掉旧 KV 之后**算的，看不到错内容，所以**不隐含错误信息**——这是 feature（时间一致性正靠它）。想保留"为什么错"必须**显式**写审计日志。
- **🟠 你给了两个互斥约束**：A 说"轮末才允许改 KV"，B 说"中途改完继续生成"。**而收益几乎全来自 B**——轮末改时后缀为 0，没有任何后缀可省。
- **🟡 别用近似注意力**（APE 那类）。你的目的是验证机制收益，引入近似 → 误差两个来源 → 无法归因。
- **🟡 区间必须统一为 token + 半开 `[start,end)`**。你的描述是闭区间，而 `seq_rm` 是 **`[p0,p1)`** —— 经典 off-by-one 来源。
- **🟡 插入的"前/后"参数有歧义**：`[A,B]` 中"B 前"和"A 后"是**同一位置**，两种表示 → 对账时以为不同实际相同。**只用 `pos`（插入到 pos 之前）**，开头/末尾自然被 `pos=0`/`pos=n` 覆盖，你担心的"被强行限定"不存在。

**建议把三种操作统一成一个原语**（减少实现与测试面）：
```
splice(start, end, new_tokens)
  replace = splice(i, j, T)   erase = splice(i, j, [])   insert = splice(p, p, T)
```

## 四、成本模型：你的收益预期需要修正

这是我认为**最需要你先想清楚**的一点：

| 方案 | 成本 |
|---|---|
| 全量重算 | $L_p \cdot c_{pre} + (L_s + L_{tail}) \cdot c_{dec}$ |
| KV 手术 | $L_n \cdot c_{dec}$ |

**三条结论**：

1. 手术省的**永远是前缀 prefill** $L_p \cdot c_{pre}$（`seq_rm`+`seq_add` 让前缀原样保留）
2. **轮末手术（后缀=0）省不到任何后缀重生成**，上限就是"一次 prefill"
3. 替换内容 $L_n$ 由模型生成，**这笔 decode 成本无法避免**

**推论**：
> 期望收益 ≈ $L_p \cdot c_{pre}$，**与输出长度无关，只与上下文长度有关**。
> **上下文越长收益越大；纯生成任务收益趋近 0。**

这解释了为什么"长代码任务"是主要受益场景，而**短命令任务**应作**负对照**——如果它也有大收益，说明测量有问题。

⚠️ 而且对 0.6B 有个现实风险（我列为 U5）：**0.6B 的 prefill 本来就极快，省下的绝对时间可能小于测量噪声**。建议阶段 1 就先测"省下的 prefill 绝对量级"，太小就该早点决定把收益验证放到更大模型上，别硬凑 0.6B 的结论。

**先说你对的那一半**——这不是空想：

新 token 的 K/V 是在**因果注意力**下对包含旧 span 的上文算出来的。自注意力是加权求和，旧 span 被 attend 到，贡献就进了新 token 的隐藏状态，进而进了它的 K 和 V。**信息确实被保留了。**

**但致命处在实现方式**：这个"保留"是靠**污染**换来的。

```
权威历史 = [A, B']            ← 旧 B 已被 B' 取代，不在历史里了
但 B' 的 KV 却是从 [A, B, B'] 算的   ← 它"记得"一个已经不存在的 B
```

后果：**后续所有 token 都会直接 attend 到一个"从未存在的历史"**。这不是近似误差，是把已删除的历史重新注入了注意力——**正是 v4.1 §4 定义的"下游扩散"，也正是你这个机制存在的理由**。用污染实现记忆，等于用病治病。

路径 C（先删旧 span 再算）        K:   0.000168   V:  0.000056
前缀部分                           :   0.000000
```

> 所以"复用 V"同样要求上文未变。

## 一、归一：破坏机制只有一条

| 操作 | 长度变化 | 后缀位置 | 后缀 KV |
|---|---|---|---|
| `replace` 等长 | $\Delta=0$ | 不变 | **可复用** |
| `replace` 变长 | $\Delta\ne0$ | 平移 | **失效** |
| `delete` | $\Delta=-(j-i)$ | 左移 | **失效** |
| `insert` | $\Delta=+m$ | 右移 | **失效** |

**本质只有一条**：$|\Delta|\ne0$ → 后缀位置整体偏移 → 后缀 K 的 RoPE 失效 → 必须重编码。

| 层面 | delete | insert |
|---|---|---|
| **后缀 KV** | ❌ 必须重算 | ❌ 必须重算 |

## 一、纠正：成本不是二分的，是三层，中间那层被漏了

你把成本看成"复用 vs 大量重算"。实际是三层：

| 层 | 操作 | 代价 | 可用性 |
|---|---|---|---|
| **L-a 位置平移** | `seq_add` 对后缀 **K** 重做 RoPE | **低** | ✅ 本地已有 |
| **L-b 表示重算** | 重算后缀**隐藏状态** → 重算 K/V | **中** | ⚠️ 可做 |
| **L-c 文本重生成** | 让模型重写后缀 | **高** | ❌ 收益归零 |

**关键事实**：`seq_add` **只重做 K**（RoPE 作用在 K 上）。**V 无位置编码，不需要重做——这是免费的。**

所以「位置偏移」本身**非常便宜**，根本不算"大量重算"。真正贵的是 **L-b**：要让后缀 K/V 反映"新历史下的注意力"，就得重算后缀的**隐藏状态**——**这已经不是"改 KV"，而是"重算一层表示"了**。

## 二、为什么「抹除」和「追加」都落在 L-b

你说得对的部分在这里，但原因需要更准确：

**抹除为什么不是删掉 KV 就完事**：K/V 是张量，能删。但"坏 token 的影响"**不只在它自己的 K/V 里**，而是**已经烘进了下游 token 的隐藏状态**。删掉它的 K/V 只是让它**不再被 attend 到**；下游 K/V 里那份被污染的表示**还在**。

**追加为什么更贵**：插入后每个后缀 token **本应 attend 到新 span**，但它的历史里没有——**"缺了一次注意力"**。补上要重算隐藏状态，**而且后缀文本可能也得改写**，再叠 L-c。

**所以代价同源于「改变了下游的注意力模式」，与"KV 长度变没变"不是同一件事。** 长度变化只带来便宜的 L-a。

## 三、你说对的核心：稠密注意力下 L-b 的代价是整条后缀

这才是"大量重算"的真正来源——**不是 KV 拼接，而是稠密注意力让影响范围无界**。

我把它写成一句可复用的判据：

> **影响范围由注意力模式决定，不由编辑操作决定。**
> 稠密注意力 → 影响范围 = 整条后缀 → 局部重算无意义。
> **稀疏注意力 → 影响范围有界 → 局部重算第一次变得有意义。**

## 四、稀疏注意力确实是结构性的借鉴，而且理由不是"更快"

| | 稠密 | 稀疏 |
|---|---|---|
| 一个历史位置被多少 query attend | **全部** | **少数** |
| 删/插一个 span 的影响范围 | 整条后缀 | **仅"选过它的那些 query"** |
| L-b 代价 | $O(\text{后缀长度})$ | $O(\text{受影响 query 数})$ |
| 局部重算价值 | 无 | **有** |

**稀疏注意力把"编辑的影响半径"从无界变成有界**——在有界影响半径下，"只重算受影响的那一小撮"才第一次成为有意义的工程。

稀疏注意力要为每个 query 维护"选中的 KV 位置集合"（检索索引）。

## 二、你还错的地方：影响范围是**跨层传递闭包**，不是"直接选中集合"

## 三、还有一个更麻烦的：重算会改变"选择"本身 → 这是**不动点问题**

```

    ↑                                │
    └──── 新选中的 K/V 又要重算 ←────┘
```

**这是自洽性问题，不是一趟扫描。** 现有文献里我没看到有人处理——**这是真空白**。

## 四、你低估的地方：这本质上是**缓存一致性问题**——而这个领域已经成熟了

你说"稀疏注意力像 CPU 的缓存与内存"。**这个类比比你以为的更准**，因为 **cache coherence 正是"局部修改导致缓存失效"的成熟解**：

| CPU 缓存 | KV 编辑 |
|---|---|
| 缓存行 | KV 块 / 稀疏块 |
| **写失效** lock | 删除该位置 KV |
| **写更新** | 就地替换该位置 KV |
| 一致性协议 (MESI) | **缺失**：没有机制保证编辑后各方视图一致 |
| **失效粒度** | **可直接借鉴**：编辑必须失效多大范围？ |
| **伪共享** | **可直接借鉴**：改 A 波及无关 B = 伪共享 |

**最值得偷的三个概念**：

2. **写失效 vs 写更新**——两种策略的取舍在 CPU 领域研究了几十年，直接类比。
3. **伪共享**——稀疏块边界导致"改 A 波及 B"，有现成对策（padding / 对齐）。

**这是 KV cache 研究尚未系统利用的框架。** 建议在开题里明确引它。

## 四、EVOKE：一个反直觉的关键结论，会改变你的方案

**Zenodo DOI 10.5281/zenodo.20467232，代码 Apache-2.0**（[github.com/Anyesh/EVOKE](https://github.com/Anyesh/EVOKE)）

它的 §3.4「Why eviction does not corrupt the cache」：

> "`seq_rm(seq, p0, p1)` frees the cells… **no dangling reference survives because Q is never cached**… `seq_add(…, delta)` … queues a **deferred RoPE shift** by δ on their K rows, **moving no bytes**. … $Q_{new}\cdot K_{survivor}$ returns **the same relative-position dot product as if the evicted range had never been decoded**; **V is position-free and untouched**. **Eviction is therefore a topological cut, not partial erasure**: its failure mode is **information loss** … **not corruption**."

**三个必须记住的**：

1. **`seq_rm` + `seq_add` 就是完整方案**（我们本地已有这两个 API）
2. **"移动零字节"**——`seq_add` 只改位置元数据，RoPE 平移延迟到下次 decode
3. ★ **删除是"拓扑切割"，不是"部分擦除"——删除不损坏缓存**

**所以我要修正上一轮我说的话**：纯**删除**之后，后缀 K 通过 `seq_add` 重新锚定，**注意力数学是良构的**。我之前的担心针对的是**替换/插入**（引入新内容），**对纯删除不成立**。

| 操作 | 是否损坏后缀 | 代价 |
|---|---|---|
| **删除** | ❌ **不损坏**（`seq_add` 修复位置） | **低** |
| 替换（等长） | ❌ 位置不损坏（但有旧影响残留 = AMORTIZE） | **低** |
| 替换（变长）/ 插入 | ⚠️ 后缀"缺了对新内容的注意力" | 中（L-b） |
